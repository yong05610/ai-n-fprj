# PaceMate AI 서비스 개선 이력 (Improvement Log)

**목적:** 발생 현상(관찰) → 원인 분석 → 개선 방향 결정(대안과 선택 이유) → 개선 설계 → 구현·검증 → 효과를 한 곳에 남겨, 미션 평가 항목 "피드백 및 개선(20%)"과 발표 자료의 "문제 해결 과정, 기술적 의사결정 근거, 개선 사항"에 그대로 쓴다. 문서 관리는 검증팀(PM)이 한다.

**작성 규칙**
- 항목마다 근거(어디서 관찰했는지: 사용자 지적, PM 검증, 테스트)를 적는다. 추측으로 원인을 쓰지 않고, 확인하지 못한 것은 "미확인"으로 쓴다.
- 효과는 측정한 값만 쓴다. 아직 못 쟀으면 상태를 "측정 예정"으로 두고 측정 방법을 적는다.
- 새 개선이 생기면 번호를 이어서 추가하고, 사용자 테스트(Phase 8~9) 결과는 "연계 사용자 테스트" 열에 링크한다.
- 용어: Grounding(근거 기반 응답), RAG(검색 증강 생성), Guardrail(출력 가드레일), Output Validation(구조화 출력 검증), Hallucination(근거 없는 생성), Human-in-the-loop(사람 검토 단계), Idempotency(멱등성), Prompt Injection(프롬프트 주입).

## IMP-001 근거 조각 사람 검토 단계 (RAG 지식 품질 관리)
- **발생 현상:** Phase 6 시작 시 `rag_documents.json` 에는 자료 10건의 메타데이터(제목, 출처, URL, 라이선스)만 있고 본문 조각(`chunks`)이 전부 비어 있었다. 튜터가 근거로 쓸 본문이 없었다.
- **원인 분석:** 본문을 만들어 넣는 작업을 개발팀(AI 보조)이 요약해서 해야 한다. 요약에는 사실 오류가 섞일 수 있고, 오류가 있으면 튜터가 **출처가 붙은 틀린 답**을 낸다(근거 있는 오답이 근거 없는 오답보다 해롭다).
- **대안과 결정:** (a) 개발팀 작성분을 바로 사용 (b) 원문을 그대로 복사 (c) 개발팀이 요약하되 `verified:false` 로 저장하고 PM 이 전수 검토한 뒤에만 `true`. (a)는 오류 위험, (b)는 CC BY-NC-SA 등 라이선스 문제로 배제. **(c) 선택**(Human-in-the-loop).
- **개선 설계:** 조각 필드 `id`, `text`, `keywords`, `verified`. 서버는 `verified:true` 조각만 색인(`rag.py`). 승인 기록은 `docs/phase6_chunk_review.md`. 승인 전에는 튜터가 항상 "참고한 등록 자료가 없어요"로 답해 근거를 만들지 않는다.
- **구현·검증:** 53조각을 PM 이 전수 검토해 사실 오류 0건 확인 후 `verified:true` 전환(커밋 63f1fe9), 기본 파일 기준 검색 테스트 추가(pytest 319건).
- **효과:** 출처 표시 답변의 근거 53조각이 사람 검토를 거침. 한계: PM 대조는 공식 문서 원문 문장 단위 비교가 아니라 알려진 사실과의 대조였다(문서에 명시).
- **연계 사용자 테스트:** 해당 없음.

## IMP-002 출처 생성 주체의 서버 분리 (Grounding 강화)
- **발생 현상(위험 식별):** 튜터 답변의 출처를 AI 가 쓰면 존재하지 않는 자료·URL 을 지어낼 수 있다(Hallucination).
- **개선 방향:** AI 는 사용한 자료의 id(`used_source_ids`)만 고르고, 제목·URL 은 서버가 검색 결과에서 만든다. AI 가 고른 id 가 이번 검색 결과에 없으면 위반으로 거부하고 재시도한다. 자료가 검색되지 않았는데 id 가 있어도 위반이다.
- **개선 설계:** `tutor.validate_tutor_answer`(Output Validation), `tutor.sources_for`(서버 생성). 결과가 없으면 서버가 "참고한 등록 자료가 없어요" 안내를 붙이고 출처 목록을 비운다.
- **검증·효과:** 실제 서버에서 자료 있는 질문(Git push/pull)에 서버가 만든 출처 1건이 붙고, 자료 없는 질문에는 출처가 비었다. AI 가 만든 출처가 화면에 나올 경로가 없다. 지어낸 출처 발생률의 전후 비교는 측정하지 않았다(구조적으로 차단).

## IMP-003 인사이트의 숫자 오류와 근거 없는 "반복 어려움" (Hallucination 방어)
- **발생 현상:** Phase 6B 검증에서 PM 이 실제 AI 를 호출했다(테스트 데이터: 기록 4건 30·31·32·20분 = 합계 113분, 회고 1건). ① 요약에 "총 **4시간 53분**"(실제 1시간 53분, 같은 문장의 "113분"은 맞음). ② 회고가 1건뿐인데 "**반복적으로** 언급되었습니다". 틀린 숫자가 저장되고 대시보드에도 표시됐다.
- **원인 분석:** ① LLM 이 합계를 스스로 계산하다 오류(산술 약점). ② 프롬프트에 "회고 두 건 이상에서 확인될 때만"이라고 적었지만 모델이 어겼고, 서버에는 이를 강제하는 검증이 없었다. 프롬프트 지시만으로는 결정적(deterministic) 보장이 없다.
- **대안과 결정:** (a) 프롬프트 문구 강화 (b) 서버가 숫자를 계산해 주고 결과 속 숫자를 검증 + 조건 규칙을 서버가 강제. (a)는 재발 가능, **(b) 선택**(Deterministic computation offloading, Guardrail).
- **개선 설계:** `window_total_minutes`, `*_label`(예 "1시간 53분")을 서버가 계산해 payload 로 전달, 응답 속 "N시간/N분/N건" 표현이 서버 값 집합에 없으면 거부·재시도. 입력 회고가 2건 미만이면 `difficulty` 는 빈 문자열이어야 하고 아니면 거부. 지시서 `docs/phase6b_fix_instructions.md`.
- **구현·검증(1차 수정, 커밋 78e45f3):** 서버 계산 `insight_rules.py` 와 검증 추가(pytest 460→518건). 원래 오류 사례를 회귀 테스트로 고정.
- **효과 측정(PM, 실제 OpenAI, 동일 데이터, 별개 사용자 7회):**
  | 지표 | 수정 전 | 수정 후 |
  |---|---|---|
  | 합계 숫자 오류(저장·표시까지 간 경우) | 1회 호출 중 1회("4시간 53분") | 0회(성공 6회 모두 서버 값과 일치, 숫자 규칙으로 거부된 시도 0건) |
  | 근거 없는 "반복 어려움"이 저장된 경우 | 1회 호출 중 1회 | 0회(서버가 거부) |
  | 인사이트 1건당 AI 호출 | 1회 | 평균 약 2회(성공 6회 중 5회가 첫 시도 거부 후 재시도, 모두 같은 사유) |
  | 502(재시도 소진) | 0회 | 1회(7회 중) |
- **2차 개선(R4):** 위 표에서 드러난 새 문제(프롬프트 규칙을 모델이 거의 매번 어김 → 비용 2배, 502 약 14%)를 `docs/phase6b_fix_instructions_2.md` 로 지시. 회고 2건 미만이면 모델에게 difficulty 를 아예 요청하지 않는 스키마로 바꾸고, 거부 사유를 종류별로 집계해 재측정한다(목표: 502 0회, 평균 호출 1.2회 이하). 결과는 이 항목에 이어 적는다.
- **2차 개선 결과(R4, 커밋 26e726a, PM 실제 OpenAI 5회, 동일 데이터):**
  | 지표 | 1차 수정 후 | R4 후 |
  |---|---|---|
  | 성공 / 502 | 6 / 1 (7회 중) | 5 / 0 (5회) |
  | 첫 시도 거부 비율 | 5/6 (모두 "회고 2건 미만인데 difficulty 작성") | 0/5 |
  | 인사이트 1건당 AI 호출 | 평균 약 2회 | 1회(추론) |
  | 평가 어조("부족" 등) | 있었음 | 5/5 없음 |
  - 회고 2건 이상에서 difficulty 를 요청하는 경로의 실제 AI 측정은 아직 없다(측정 예정: 회고 2건 이상 데이터로 5회).
- **교훈(발표용):** 프롬프트 지시는 보장이 아니다. 서버 검증은 오류를 막지만 모델이 같은 위반을 반복하면 비용으로 돌아오므로, 위반이 불가능하도록 입력·스키마를 설계하는 것이 근본 해법이다.
- **한계(수용):** 한글 숫자("세 시간")와 "N개" 표현은 검증하지 않는다. 회고 2건 이상일 때 "반복"의 의미적 근거는 서버가 확인할 수 없다.
- **연계 사용자 테스트:** Phase 8 에서 인사이트 정확성 체감을 설문에 포함할 것.

## IMP-004 학습 자료 접근성 개선 (실시간 웹검색 대신 서버 생성 링크)
- **발생 현상:** 사용자가 "자료를 제시할 때 실시간 웹검색이 없어 AI 답변이 한정적이고 빈약해 보이고, 학습에 참고할 실자료도 부족하다"고 지적했다(2026-10-24).
- **원인 분석(코드로 확인):** 검토된 자료가 10건이라 대부분의 분야에서 출처가 없고, 자료가 없으면 학습자가 다음에 무엇을 찾아볼지 단서가 없다. 분야 매칭은 분야 문자열의 첫 토큰이 정확히 같을 때만 성립해(예: "Python 개발"→python) AI 가 만든 자유 입력 분야에는 거의 맞지 않는다. AI 답변 자체는 자료가 없어도 일반 지식으로 가능하나, 출처·참고 링크가 없어 빈약해 보인다.
- **대안과 결정:**
  - (a) 실시간 웹검색(OpenAI 웹검색 도구): 출처 신뢰성 검증 불가, 비용·지연, 외부 글이 프롬프트에 들어오는 Prompt Injection 위험, 배포 일정 부담 → **MVP 에서는 보류**(사용자 테스트에서 자료 부족 지적이 많으면 허용 도메인 목록과 함께 재검토, backlog).
  - (b) 검토된 자료 본문 조각 대량 추가: 시간 부족.
  - (c) 링크 전용 검토 자료 확장 + 서버가 만드는 검색 링크 + 튜터가 이어서 찾을 키워드 제안: **선택.** 근거(출처)와 참고 링크를 분리해 "근거 있는 것처럼 표시하지 않는다"는 핵심 결정을 지킨다.
- **개선 설계:** ① 링크 31건을 PM 이 실제로 열어 확인해 추가(`docs/phase6c_resource_links.md`), 튜터 출처로는 쓰지 않음. ② 분야 매칭을 `tags` 기반 토큰 일치 점수로 개선(정밀도 우선, 부분 문자열 금지). ③ 학습 정보로 서버가 만드는 구글·유튜브 검색 링크("검토 전 외부 링크" 라벨). ④ 튜터가 출처 없는 답변에서 `search_keywords` 2~3개를 제안(URL 금지 검증). 지시서 `docs/phase6c_dev_prompt.md`.
- **구현·검증(커밋 67d0a46, PM 검증):** 링크 31건이 PM 목록과 일치함을 확인, 서버 생성 검색 링크 3종, 튜터 `search_keywords`(실제 AI 로 출처 없는 질문에 키워드 3개와 안내 부착 확인). pytest 539→597건.
- **검증에서 발견한 문제:** 분야 매칭이 자유 입력 분야에서 약하다. 실제 테스트 학습(VIBE CODING / 웹 개발의 기초)이 빈 결과였고 한글 별칭("파이썬", "자바스크립트")과 "AI"도 맞지 않았다. 그 결과 튜터의 `related_links` 와 계획 화면의 참고자료가 그 학습에서 비었다. 분야 점수가 0 이면 과정 토큰으로 보완 매칭하고, 기존 10개 자료에 한글 별칭 tags 를 추가하도록 수정 지시(`docs/phase6c_fix_instructions.md`). 정밀도 우선 원칙(Java≠JavaScript, 일반어만 일치하면 제외)은 유지.
- **수정 결과(커밋 6abf810, PM 직접 시험):** 시험 입력 24건 중 기대한 매칭 15건이 모두 나옴(수정 전에는 실제 테스트 학습 VIBE CODING / 웹 개발의 기초, 파이썬, 자바스크립트, AI 가 빈 결과). 무관 입력 5건(요리, 개발/기초 등)은 계속 빈 결과. pytest 597→623건.
- **추가 설계 결함 발견:** 튜터의 "함께 보면 좋은 자료"가 출처 있는 답변에서만 나오도록 한 설계(PM 지시) 때문에, 출처가 드문 실제 질문에서는 학습에 맞는 검토된 링크가 보이지 않았다(실제 AI 호출로 확인). 출처 유무와 무관하게 붙이고 질문과 겹치는 링크를 앞에 두도록 수정 지시(`docs/phase6c_fix_instructions_2.md`).
- **R4 결과(커밋 4e038c0, PM 실제 AI 4회):** 관련 링크가 출처 유무와 무관하게 붙음. 매칭되는 학습 3건 중 3건(웹, Python 포함)에서 `related_links` 가 채워졌고(수정 전 웹 학습은 빈 목록), 자료가 없는 분야(요리)는 키워드와 검색 링크로 대체됨. pytest 623→637건.
- **효과: 부분 측정 완료, 사용자 지표는 측정 예정(Phase 8).** 지표: (1) 연결된 참고자료가 1건 이상 나오는 학습 비율(개선 전: 10건 기준 첫 토큰 일치, 개선 후: 분야 문자열 N종으로 측정), (2) 출처 없는 튜터 답변에서 키워드·검색 링크가 붙는 비율, (3) Phase 8 설문의 "참고자료 도움 정도" 점수.
- **연계 사용자 테스트:** Phase 8 설문에 "참고자료가 학습에 도움이 되었는가(1~5)" 문항 포함.

## IMP-005 튜터 질문 범위 통제 (학습 관련 질문만 응답)
- **발생 현상(위험 식별):** 튜터가 학습과 무관한 질문에도 답하면 서비스 목적을 벗어나고 비용·안전 위험이 생긴다. 별도 분류 호출을 두면 호출 수와 지연이 늘어난다.
- **결정·설계:** 별도 분류 호출 없이 한 번의 구조화 출력 `{relevant, answer, used_source_ids}` 로 판정한다. `relevant=false` 이면 AI 가 쓴 답은 버리고 서버의 고정 거절 문구를 저장한다. 관련 있는 질문이 거절된 경우 다시 물을 수 있게 안내를 문구에 포함한다.
- **검증·효과:** 실제 호출에서 무관 질문(요리)이 거절 문구로 처리되고 출처가 비었다. AI 호출 1회로 처리(추가 호출 0회). 오거절률은 아직 측정하지 못했다(측정 예정: 사용자 테스트 질문 로그가 아닌 관찰·메모 기반, 로그에 질문 원문을 남기지 않는 원칙 때문).

## IMP-006 계획 수립 흐름 개선 (1차 사용자 테스트 반영)
- **발생 현상:** `docs/user_test_round1.md` 의 지적: 목표 선택 목록이 이전 등록 내용으로 나오고(AI 추천 목록이어야 함), 시작일이 첫 월요일로 고정되며, 일정이 겹치면 계획을 저장할 수 없고(안 겹쳐도 겹친다는 오류, 날짜를 고쳐도 같은 오류, 한 가지가 아니라 두 개 이상 겹침을 안내해야 함).

- **개선 설계·검증:** 시작일 직접 선택(과거 400), 겹침 전부 안내와 날짜 변경 시 오류 해제, 규칙을 한 날 최대 2개로 재정의(경계 분할 알고리즘, 같은 날 3번째만 409). 실제 서버에서 예시 4건의 허용·거부가 지시서와 일치(`docs/phase5c_fix_verification.md`), pytest 258→274건.
- **효과:** 1차 지적 6번(겹침 오류)과 8번을 dev 모드에서 해소. 사용자 재확인은 Phase 8 로 예정.
- **연계 사용자 테스트:** `docs/user_test_round1.md` 의 PM 검증 표.

## IMP-007 튜터 출처의 어색함 (관찰 중)
- **발생 현상:** 사용자 캡처에서 "데이터 분석을 공부할 때 어떤 부분이 중요할까?"라는 일반 질문에 SQL 문서가 출처로 붙었다(답변이 SQL 을 한 요소로 언급했고 검색이 "데이터"로 SQL 조각을 골랐기 때문).
- **판단:** 규칙 위반은 아니다(출처는 검토된 자료이고 답변이 실제로 언급함). 다만 "git push" 질문에 JavaScript 배열 `push` 조각이 2순위로 따라오는 교차 일치도 확인됐다.
- **보류 사유·다음 단계:** 사용자 테스트에서 어색하다는 지적이 나오면 검색 가중치(키워드 가중, 동점 처리, 분야 가중) 조정을 개선 항목으로 올린다(`docs/post_mvp_backlog.md`). 현재는 데이터가 부족해 조정 기준을 정할 수 없다.

## IMP-008 첫 주 이후 계획 공백 → 전체 과정 일괄 계획 (결정적 배치로 AI 산술 의존 제거)
- **발생 현상:** 사용자가 계획 화면에서 "주간 계획이라는 말만 나오는데 이 계획 세트가 종료 때까지 반복되는 것이냐"고 질문했다(2026-10-25). 코드로 확인하니 AI 가 첫 주 한 주치(3~6개)만 만들고 확정 때 시작 주 하나에만 저장하며, 그 이후 주는 계획이 없고 자동 반복도 없었다. 목표일이 몇 달 뒤여도 첫 주가 지나면 이번 주 과제가 비고 대시보드의 오늘 추천 과제도 사라진다.
- **원인 분석:** PRD 가 "목표 완료 희망일을 넘는 주간 계획은 생성하지 않는다"는 **상한 규칙만** 두고 그 사이 주들을 만드는 방법을 정하지 않았다(설계 공백). "주간 계획"이라는 용어가 한 주 계획만 만든다는 구현으로 이어졌다.
- **대안과 결정:** (a) 같은 과제 세트를 매주 반복 복사: 학습은 1장, 2장, 3장을 한 번 지나가는 것이므로 의미 없어 사용자가 배제. (b) 사용자가 요청할 때마다 다음 주 계획을 AI 로 생성: 맞춤형이지만 첫 사용 흐름에서 계획이 비는 문제가 남음. (c) **전체 과정을 한 번에 순서대로 계획 + 주차 배치는 서버 계산:** 선택(사용자 결정 2026-10-25). 과제 시간은 학습자 수준 차이에 따라 AI 가 정하고 한 과제가 한 주를 넘을 수 있으며, 총합은 가용 시간 이하, 기존 학습은 새로 만든다.
- **개선 설계:** AI 는 순서 있는 과제 목록(3~60개, 제목 중복 금지)과 각 예상 분만 낸다. 서버가 가용 시간(주당 분 × 주 수)을 계산해 총합을 검증하고, 과제를 타임라인에 이어 붙여 시작 주와 추천 요일을 결정적으로 계산한다(6B 교훈: 산술·배치는 서버, 판단은 AI). 화면은 총 소요 시간, 이번 주·오늘 예정 시간을 보여 준다. 설계 `docs/phase5f_design.md`, 지시서 `docs/phase5f_dev_prompt.md`.
- **구현·검증(커밋 ee2c511, PM 검증):** 서버 배치 모듈과 공유 테스트 벡터(pytest 597→724건, 프론트 72→115건). PM 의 설계 예시 재현, 무작위 2000개 계획 속성 시험 위반 0, 확정 때 클라이언트 조작 값 무시 확인, 긴 과제(주당 시간 초과)와 옛 데이터 호환 확인.
- **검증에서 발견한 문제:** (1) 가용 시간을 월요일 기준 주 단위로 통째로 세어 실제보다 최대 약 1주분 크게 계산(시작일 일요일·60일 기간에서 약 15%). 일수 기준 가용 시간으로 수정 지시. (2) 실제 AI 가 긴 기간(26주·주 15시간)에서 과제 10개, 가용의 15%만 계획(짧은 기간 62~92%). 프롬프트 보강, 가용 대비 비율 표시와 안내, 실제 AI 3회 재측정으로 대응(필요하면 하한 검증).
- **수정 결과(커밋 bee3e07, PM 검증):** (1) 가용 시간을 실제 일수로 계산(일요일 시작·61일: 3000분 → 2614분, 월~일 한 주는 동일), 공유 벡터 11개 케이스. pytest 724→756건, 프론트 115→132건. (2) 긴 기간 분량: 프롬프트 권고와 `coverage_percent` 안내를 넣었으나 실제 AI 측정(26주·주 15시간)에서 분량은 오르지 않음(개발팀 13%, PM 실측 15% → 13%). PM 이 임시 하한 검증(40% 미만 거부)을 실험했더니 3회 중 2회가 재시도 3번 모두 거부되어 502(22.8초, 19.2초), 성공 1회는 처음부터 52%(24개)로 **편차가 큼**. 하한 검증은 도입하지 않고 화면 안내만 유지, 구간 분할 생성은 MVP 이후 후보(backlog).
- **교훈:** 모델이 따르지 않는 분량 규칙은 거부·재시도로 강제하면 오류율만 올린다. 이럴 때는 규칙을 강제하는 대신 구조(구간 분할)를 바꾸거나 사용자에게 안내하는 편이 낫다(6B 의 "어길 수 없게 설계"와 같은 원칙이지만 여기서는 비용이 커서 보류).
- **효과: 부분 측정 완료.** 계획이 목표일까지의 주를 덮는 구조로 바뀜(개선 전: 첫 1주만). 계획 생성 지연은 실제 호출 5~7초, 모델 호출 1회(개발팀 3회·PM 2회, 과제 6~10개). 사용자 지표는 측정 예정. 지표: (1) 확정한 계획이 목표일까지의 주 수를 덮는 비율(개선 전: 첫 1주만, 개선 후: 전 주), (2) 계획 생성 AI 지연(초)과 재시도 횟수(과제 최대 60개로 응답이 길어짐), (3) 사용자 테스트에서 "다음 주에 할 일이 없다"는 지적 수.

## IMP-009 지식 기반(참고자료) 확장성 — 큐레이션 파이프라인 로드맵 (계획)
- **발생 현상:** 사용자가 "AI 가 학습 분야·목표에 맞는 자료를 찾아 계속 쌓거나, 사용자와 PM 이 자료를 쌓는 것이 서비스 질을 지속적으로 고도화하는 데 중요하지 않은가"라고 제안했다(2026-10-25). 현재는 자료 쓰기 경로가 없고(서버는 읽기만, 자료는 저장소의 JSON 에 고정) 분야가 늘어도 자료가 저절로 늘지 않는다.
- **원인 분석(코드·측정):** 검토된 자료는 41건(조각이 있는 문서 10건·조각 53개, 링크 31건), 분야 9개. 자료 공백을 집계하는 장치와 승인 흐름의 DB 경로가 없어 수동 추가만 가능하다.
- **대안과 결정:** (a) AI 가 찾은 자료를 바로 노출: 틀린 링크, 저작권, 스팸, 프롬프트 주입 위험으로 배제(IMP-004 와 같은 이유). (b) 사용자 파일 업로드: 개인정보·저작권·악성 파일 위험으로 배제. (c) **후보 수집은 자동·반자동, 노출은 사람 승인 후**의 단계적 파이프라인(S0~S8): 선택.
- **개선 설계(계획):** 자료 공백 집계(원문·UID 없이 분야 건수만) → 후보 큐 → 관리자 "참고자료 관리"(승인·반려, DB 읽기 경로) → 자료 평가 신호 → 링크 자동 점검 → (선택) 사용자 링크 제안, 허용 도메인 웹검색 후보 발굴. `docs/resource_curation_roadmap.md`.
- **구현·검증:** MVP 에서는 S0(완료)까지, S1(수동 확장)은 요청 시 즉시. 이후 단계는 Phase 8 설문(참고자료 도움 1~5)과 자료 없음 분야 집계로 판단한다.
- **효과: 측정 예정(Phase 8 기준선).**
