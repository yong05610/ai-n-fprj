# 계정 승격 설계 — 기기를 바꿔도 이어 쓰기 (PM, 2026-10-25, 초안·결정 대기)

상태: **설계 초안.** 개발 지시서는 아래 "결정 필요" 항목을 사용자가 정한 뒤에 쓴다. 사용자 테스트(Phase 8) 전에 구현할지, 테스트 결과를 보고 구현할지도 사용자 결정이다. 이 문서는 코드를 바꾸지 않는다.

## 1. 문제
익명 로그인은 **브라우저 저장소**로 사용자를 식별한다(같은 브라우저 프로필 + 같은 주소 = 같은 UID).
- 기기·브라우저·주소가 바뀌거나 사이트 데이터를 지우면 새 사용자가 되어 기존 데이터에 접근할 수 없다.
- 공용 PC에서는 앞 사람의 데이터가 다음 사람에게 보인다.
- 관리자(ADMIN_UIDS)도 UID 기준이라 주소가 바뀌면 다시 등록해야 한다.

## 2. 후보 방식
| | A. 구글 계정 연결(승격) | B. 복구 코드(이메일 없음) | C. 이메일 링크 / 이메일+비밀번호 |
|---|---|---|---|
| 방법 | 익명 계정에 구글 계정을 연결. UID 유지 | 서버가 무작위 복구 코드를 발급, 사용자가 보관. 새 기기에서 코드를 입력해 같은 UID로 로그인 | 이메일로 로그인 |
| 수집 정보 | 이메일(구글 제공), 표시 이름 가능 | **없음**(코드는 개인을 가리키지 않는 무작위 값) | 이메일 |
| 사용자 편의 | 높음(익숙함) | 낮음(코드를 잃으면 복구 불가, 코드가 비밀번호 역할) | 중간 |
| 공용 PC 보호 | 로그아웃 후 본인 계정 로그인 | 로그아웃 후 코드 입력 | 같음 |
| 서버 변경 | 거의 없음(토큰의 UID 원칙 유지) | **있음**: 코드 검증 후 Firebase 사용자 지정 토큰 발급, 무차별 대입 방지(시도 제한) | 거의 없음 |
| 위험 | 이메일 개인정보 처리, 충돌 처리 | 코드 유출 = 계정 탈취, 코드 분실 = 영구 손실, 서버 보안 구현 부담 | 이메일 개인정보 처리, 메일 지연 |
| 학교 환경 | 학교 구글 계정은 외부 앱 로그인이 막힐 수 있음(확인 필요) | 영향 없음 | 영향 작음 |

PM 의견: 대상이 **개인정보 수집을 최소화해야 하는 학습자**(미성년 포함 가능)이면 B 를 먼저 검토할 가치가 있다. 사용자 편의와 보안 구현 부담을 고려하면 A 가 기본 추천이다. **둘을 함께 제공**(A 기본, B 는 "이메일을 주고 싶지 않은 사람용")하는 안도 가능하나 개발량이 늘어난다.

## 3. 이메일의 법적 취급 (개인정보보호법) — 확인된 것과 확인하지 못한 것
사용자 질문: "이메일과 PaceMate 암호만 있고 다른 개인정보와 연결되지 않으면(이메일 1개 단일) 예외에 해당할 수 있지 않을까?"

**확인한 것(검색한 공개 해설 자료 기준, 법령 원문과 유권해석은 직접 확인하지 못함):**
- 개인정보보호법 제2조 제1호 나목: 그 정보만으로 특정 개인을 알아볼 수 없어도 **다른 정보와 쉽게 결합하여 알아볼 수 있으면** 개인정보다. 쉽게 결합 가능한지는 입수 가능성, 시간·비용·기술을 합리적으로 고려해 판단한다.
- 해설 자료는 이메일 주소를 성명, 학번, 아이디 등과 함께 개인정보의 예로 든다.
- 결합 대상인 "다른 정보"는 처리자가 직접 가진 것이어야 하는 것은 아니다(제3자 보유 정보도 포함될 수 있다는 해설).
- 만 14세 미만 아동의 개인정보를 처리하려면 법정대리인의 동의가 필요하다(제22조 제5항 취지).
- 처리방침에서 국외 이전은 위탁·제3자 제공과 구분해 별도로 기재해야 한다(이전 항목, 국가, 시기와 방법, 받는 자, 이용 목적과 보유 기간, 거부 방법 등).

**PM 판단(법률 자문 아님):**
- "이메일 하나만 있고 비밀번호도 우리 서비스 전용이므로 개인정보가 아니다 / 예외다"라고 **볼 근거를 찾지 못했다.** 이메일 주소는 흔히 실명이나 소속을 포함하고, 구글 계정이면 구글이 이메일과 사람을 연결해 갖고 있어 "쉽게 결합"될 수 있다. 비밀번호를 우리 서비스 전용으로 둔다고 해서 이메일이 개인정보가 아니게 되지 않는다. **개인정보로 보고 설계하는 것이 안전하다.**
- 법은 "수집을 하지 말라"가 아니라 **수집하면 지켜야 할 것**(필요 최소한만 수집, 이용 목적 고지와 동의, 보유·파기, 안전조치, 처리방침 공개, 국외 이전 고지, 아동 동의)을 정한다. 이메일을 수집하면 이를 갖추어야 한다.
- 이메일을 **아예 받지 않는 방식(B)** 은 이 부담을 줄인다. 단 학습 기록·회고에 사용자가 직접 쓴 내용은 이미 개인적일 수 있다(현행 동의 문구로 다루는 범위인지는 아래 확인 필요).

**확인하지 못한 것(결정 전에 확인):**
- 최소수집 원칙의 구체 조문, 소규모 서비스·비영리·교육 시범 운영에 대한 완화나 예외 유무.
- 이 서비스가 법적으로 누구에게 "개인정보처리자"인지(개인, 팀, 학교·기관 산하 여부)와 책임 주체.
- 현재 동의 문구(v1.1)가 Firebase(미국 등)·OpenAI로의 국외 처리·이전을 충분히 고지하는지. **이미 해당되는 사안일 수 있다.**
- 대상 이용자에 14세 미만이 포함되는지.
→ **조치:** 사용자가 소속 기관(개인정보 담당)이나 개인정보보호위원회 안내(개인정보 보호 포털·상담 번호)에 위 항목을 문의한다. 문의 결과 전에는 A·C 를 운영에 켜지 않는다.

## 4. 설계 원칙 (어느 방식이든 유지)
- UID 는 **토큰에서만** 정한다. 서버가 요청 본문을 믿지 않는 원칙은 그대로.
- 승격은 **선택**이다. 익명으로도 계속 쓸 수 있다(데이터 보존 안내 포함).
- 동의 전에는 계정도 개인정보도 만들지 않는다. 이메일을 수집하는 방식은 약관 버전을 올리고 **별도 동의**를 받는다.
- 삭제 요청은 계정, 이메일, 연결 정보까지 지운다.
- 로그에 이메일, 복구 코드, 토큰을 남기지 않는다.

## 5. 충돌 규칙 (방식 A, C)
이미 다른 UID에 연결된 계정으로 연결을 시도하면 Firebase가 오류(`credential-already-in-use`)를 준다.
- **MVP 규칙(추천):** 합치지 않는다. 안내 "이 계정은 이미 다른 학습 기록과 연결돼 있어요. 그 기록으로 로그인할까요? 지금 기기에서 만든 학습은 이 기기의 임시 기록으로 남고, 로그인하면 보이지 않아요." 로그인에 동의하면 그 계정의 UID로 전환한다. 임시 기록은 삭제되지 않지만 접근할 수 없다(안내문에 명시).
- 합치기는 데이터 충돌(중복 과제, 진행률)이 크고 위험해 후보에서 제외한다.

## 6. 방식 B 설계 메모 (선택 시)
- 발급: 소유자가 설정에서 "복구 코드 만들기" → 서버가 충분히 긴 무작위 값 생성, **서버에는 해시만 저장**, 화면에 한 번만 표시하고 저장 안내.
- 사용: 새 기기에서 코드 입력 → 서버가 해시 비교 → Firebase 사용자 지정 토큰 발급 → 같은 UID.
- 필수 보안: 시도 횟수 제한(IP·코드별), 무차별 대입 방어, 코드 재발급·폐기, 로그에 코드 금지.
- 한계: 코드를 잃으면 복구 불가, 코드가 유출되면 탈취 가능. 사용자 안내가 중요.

## 7. 구현 단계(안, 결정 후 확정)
1. 설계 확정: 방식(A/B/둘 다), 동의 문구와 약관 버전, 삭제 정책, 충돌 규칙. PM 작성 + 사용자 승인.
2. 콘솔 설정(사용자): 방식 A 면 Firebase Authentication 의 Google 사용 설정. (공개 이름·지원 이메일 입력, 승인된 도메인 확인)
3. 개발: 화면(연결, 로그인, 로그아웃, 충돌 안내), 서버(삭제 확장, B 면 코드 발급·검증), 테스트.
4. PM 검증: 연결 후 UID 유지, 새 브라우저 로그인으로 같은 데이터, 충돌 시나리오, 삭제 시 계정 제거, 로그 확인.
5. 운영: 처리방침·테스터 안내문 갱신, 관리자 등록(UID 기준) 절차 갱신.

## 8. 운영 변경 (방식 무관)
- 테스터 안내문: 개인 브라우저 사용, 공용 PC는 시크릿 창, 사이트 데이터 삭제 시 새로 시작됨(승격 전까지).
- 설문 추가: "다른 기기에서도 이어 쓰고 싶은가"(1~5), "계정 연결(구글/코드)을 쓸 의향"(예/아니오/이유).
- 관리자: UID 가 주소·브라우저마다 달라 배포 사이트의 UID 로 ADMIN_UIDS 를 등록(현재 절차). 승격 후에도 UID 는 유지되므로 한 번 등록하면 기기를 바꿔도 유지된다.

## 9. 결정 필요 (사용자)
1. 방식: A(구글), B(복구 코드), 둘 다, 또는 보류.
2. 시기: Phase 8 사용자 테스트 **전에** 구현 / 테스트 결과를 보고 **후에** 구현. (PM 추천: 후. 테스트로 필요성을 먼저 확인)
3. 법적 확인: 기관·개인정보위 문의 담당과 결과 반영 시점(§3 확인 항목).
4. 충돌 규칙 §5 승인.
