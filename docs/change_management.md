# 변경관리 문서 (MVP 이후 새 기능·변경의 단일 기록)

작성: 검증/PM, 2026-10-26. 사용자 결정(2026-10-26): **새 기능과 변경의 정리는 TASK.md 가 아니라 이 문서에서 한다.**

## 1. 역할 구분
| 문서 | 역할 |
|---|---|
| `TASK.md` | **원래 MVP 14일 계획과 완료 이력.** 더 늘리지 않는다(동결). 이미 들어 있는 5B~6C 등은 그대로 둔다 |
| **이 문서** | 2026-10-25 이후 요청·결정된 **변경 한 건당 한 줄**과 상태, 근거 문서 링크, 영향 범위, 검증 상태 |
| 설계·지시서·보고서·검증 문서 | 각 변경의 상세(`docs/…`). 이 문서에는 **링크만** 둔다 |
| `docs/post_mvp_backlog.md` | 아직 결정되지 않은 후보. 결정되면 이 문서에 변경 번호(CR)를 받아 옮긴다 |
| `docs/ai_improvement_log.md` | 발표·평가용 개선 이력(현상, 원인, 결정, 효과). 변경이 끝난 뒤 PM 이 추가 |

## 2. 운영 규칙
1. **새 요청은 먼저 CR 번호를 받는다**(`CR-NNN`, 번호는 재사용하지 않는다). 번호 부여는 PM 이 한다.
2. 한 줄에 **무엇을, 왜, 누가 결정했나(날짜), 영향, 상태, 근거 링크**를 적는다. 상세는 별도 문서에 쓰고 여기에는 쓰지 않는다.
3. **상태**: `요청` → `설계` → `승인대기` → `개발` → `검증` → `배포대기` → `완료`. 보류는 `보류`, 다른 변경에 흡수되면 `흡수(CR-NNN)`.
4. **"완료"는 PM 이 직접 검증하고 배포 환경에서 확인한 뒤에만** 쓴다. 확인하지 못한 것은 "미검증"으로 남긴다(체크박스 대신 검증 열에 쓴다).
5. **영향**에는 문서(PRD, ERD, DFD, 동의 문구, 가이드)와 코드 영역, 데이터, 배포 설정을 적는다. **도면(ERD, DFD, 구성도)은 구현·검증이 끝난 뒤 또는 이슈가 있을 때만 고친다**(2026-10-26 결정).
6. 사용자에게 보이는 동작이 바뀌거나 개인정보 처리가 바뀌는 변경은 **동의 문구 영향**을 반드시 적는다.
7. push 와 배포 시점은 사용자가 정한다. 대기 중인 로컬 커밋 수를 매번 적을 필요는 없고 아래 §4 "배포 대기"에서 관리한다.
8. 개발팀 지시서는 한 번에 하나만 내보낸다(CLAUDE.md 진행 원칙).

## 6. 새 변경을 추가하는 방법
1. 이 문서 §3 맨 아래에 새 CR 한 줄을 추가한다(상태 `요청`).
2. 필요하면 `docs/` 에 설계 또는 지시서를 쓰고 링크를 단다(파일 이름에 CR 번호를 쓰지 않아도 된다).

4. 끝나면 `docs/ai_improvement_log.md` 에 개선 이력을 추가할지 PM 이 판단한다.
