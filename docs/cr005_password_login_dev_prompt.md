# CR-005 개발 지시서 — 암호로 다른 기기에서 이어 쓰기

작성: 검증/PM, 2026-10-27. 근거: `docs/auth_upgrade_design.md` §E(방식 E)와 **§11(2026-10-27 사용자 결정)** 을 먼저 읽는다. 이 지시서와 설계가 충돌하면 **§11 → 이 지시서 → §E** 순으로 따르고 보고서에 알린다. 변경 기록은 `docs/change_management.md` CR-005.

**진행 규칙:** 전부 구현한 뒤 `docs/cr005_password_login_report.md` 로 보고하고 **멈춘다.** 채팅에는 한 줄 요약(완료 여부, 테스트 수, 파일 경로)만 남긴다. **커밋까지만 하고 push 하지 않는다**(PM 보안 검증 후 사용자가 시간을 정한다). 사용자 테스트(TASK Phase 8)는 이 기능이 배포된 뒤 시작한다.

## 0. 무엇을 만드나 (사용자 흐름)
1. 지금처럼 동의 → 익명(브라우저) 인증으로 시작해 쓴다. **바뀌지 않는다.**
2. [내 정보·설정]의 새 카드 "다른 기기에서 이어 쓰기"에서 **암호와 암호 확인**을 입력해 등록한다. 이 학습 기록(UID)에 암호가 연결된다. UID 와 데이터는 그대로다.
3. 다른 기기(또는 새 브라우저)에서 처음 들어오면 동의 창에 **"이미 암호를 등록했어요(사용자 인증)"** 가 있다. 암호만 입력하면 같은 UID 로 들어와 같은 학습 기록을 본다.
4. 암호 규칙: **8자 이상 64자 이하, 영문·숫자·특수문자를 모두 포함**, 공백 없음, 출력 가능한 ASCII 만(사용자 결정).

## 1. 지켜야 할 조건 (빼면 승인하지 않는다)
1. **UID 는 토큰에서만 정한다**(CLAUDE.md 핵심 결정). 암호 로그인은 서버가 암호로 UID 를 찾은 뒤 **Firebase 사용자 지정 토큰(custom token)** 을 발급하고, 프론트가 `signInWithCustomToken` 으로 로그인하는 것이다. 그 뒤 모든 API 는 지금처럼 ID 토큰으로 UID 를 정한다. 요청 본문의 UID 를 믿지 않는다.
2. **기본 꺼짐:** 환경변수 `PASSWORD_LOGIN_ENABLED`(기본 `false`). 꺼져 있으면 새 API 는 404, 화면에 새 카드·링크가 보이지 않는다. 지금 배포에 그대로 올라가도 사용자에게 달라지는 것이 없어야 한다. 프론트는 `/health` 응답의 새 필드 `password_login_enabled` 로 표시 여부를 정한다(Vercel 환경변수를 늘리지 않는다).
3. **암호 원문을 어디에도 저장·기록하지 않는다.** 로그, 오류 응답, 예외 메시지, 테스트 출력, 보고서, 브라우저 저장소(localStorage 등)에 암호와 해시를 남기지 않는다. `caplog` 로 시험한다.
4. **동의 전에는 익명 UID 를 만들지 않는다.** 새 기기에서 암호로 로그인하는 동안 `signInAnonymously` 를 부르지 않는다.
5. 기존 테스트(pytest 1264, 프론트 183)는 기대값을 고치지 않고 통과해야 한다. 고쳐야 하면 이유를 보고한다.
6. `backend/.env`, `frontend/.env.local` 을 수정하지 않는다. 비밀값을 코드·문서·채팅에 쓰지 않는다.

## 2. 백엔드
### 2-1. 저장 방식 (설계 §E-2 의 3·8번)
- 찾기 키: `key = scrypt(password_utf8, salt=AUTH_PEPPER, n=2**14, r=8, p=1, dklen=32).hex()`(표준 라이브러리 `hashlib.scrypt`, 새 의존성 없음). 같은 암호는 같은 키가 나와야 하므로 사용자별 salt 는 쓰지 않는다. 대신 서버만 아는 `AUTH_PEPPER` 를 섞는다.
- `AUTH_PEPPER`: 환경변수(32자 이상). `PASSWORD_LOGIN_ENABLED=true` 인데 없거나 짧으면 **시작을 거부**한다(`deploy_config.py` 의 기존 방식, 메시지에 변수 이름만). dev 모드 테스트에서는 테스트용 값을 주입한다. 값을 바꾸면 등록된 모든 암호가 무효가 된다는 것을 보고서와 배포 안내에 적는다.
- 새 컬렉션 `credentials`: 문서 ID = `key`, 필드 `{uid, created_at}`. **`USER_OWNED_COLLECTIONS` 에 넣지 않는다**(문서 ID 가 해시라 일반 소유 조회 대상이 아님). 사용자 문서에는 `password_enabled: true`, `password_set_at` 만 둔다(**키·해시를 users 에 두지 않는다.** users 는 본인이 Firestore 에서 직접 읽을 수 있는 규칙이다).
- `firebase/firestore.rules`: `credentials` 는 누구도 읽기·쓰기 불가임을 명시하는 규칙을 추가한다(지금도 기본 거부지만 의도를 드러낸다).
- 해시 계산 시간을 이 PC 에서 재서 보고한다(Render 무료 서버 측정은 PM).

### 2-2. API
| API | 인증 | 동작 |
|---|---|---|
| `POST /api/auth/password` | `require_consented_uid` | 등록·변경. 본문 `{password, client_request_id}`. 규칙 검사(§0-4) → 흔한 암호 검사(§2-3) → 키 계산 → 다른 UID 가 쓰는 키면 **409 `PASSWORD_UNAVAILABLE`** → 이미 이 UID 의 암호가 있으면 옛 키 문서를 지우고 새 키로 바꾼다 → `users.password_enabled=true`. 같은 `client_request_id` 재시도는 같은 결과(멱등). |
| `DELETE /api/auth/password` | `require_consented_uid` | 암호 로그인 끄기. 이 UID 의 키 문서 삭제, `password_enabled=false`. 없으면 그대로 200. |
| `POST /api/auth/password/login` | **없음**(새 기기라 토큰이 없다) | 본문 `{password}`. 시도 제한(§2-4) 확인 → 키 계산 → 있으면 `{custom_token}` 200, 없으면 **401 `LOGIN_FAILED`**. 규칙에 맞지 않는 암호도 같은 401(규칙을 알려 주지 않는다). |
| `GET /api/user/profile` | 기존 | 응답에 `password_enabled`(불리언), `password_set_at` 추가 |
| `/health` | 기존 | `password_login_enabled`(불리언) 추가 |

- `custom_token`: firebase 모드는 `firebase_admin.auth.create_custom_token(uid, app=get_firebase_app())`. **dev 모드**는 `"dev-<uid>"` 를 그대로 돌려주고 프론트 dev 세션이 그 UID 를 저장한다(키 없이 개발·테스트 가능).
- `409 PASSWORD_UNAVAILABLE` 메시지는 **흔한 암호 거부와 같은 문장**: "이 암호는 쓸 수 없어요. 다른 암호를 정해 주세요." (겹침인지 흔한 암호인지 구분해 알려 주지 않는다. 설계 §E-2 5번). 길이·문자 종류 위반은 422 로 규칙을 알려 줘도 된다(누구나 아는 규칙).
- 로그인 실패 응답은 성공·실패 모두 해시를 계산하고, 실패 시 **고정 지연(예: 300ms)** 을 더해 시간 차이로 정보를 주지 않는다.
- 오류는 기존 `ErrorResponse` 형식. 새 오류 코드는 `schemas.py` 와 프론트 타입에 추가.

### 2-3. 흔한 암호 거부 (설계 §E-2 2번)
- `backend/data/common_passwords.txt`: 공개된 흔한 암호 목록 중 **이 규칙(8자 이상, 세 종류 포함)을 통과할 수 있는 형태를 포함해 1,000개 이상**. 출처와 라이선스를 파일 머리 주석과 보고서에 적는다(라이선스가 불분명한 목록은 쓰지 않는다). 비교는 대소문자 무시.
- 패턴 거부: 같은 문자 4번 이상 연속, 키보드·숫자·알파벳 연속 4자 이상(`qwer`, `asdf`, `1234`, `abcd` 와 그 역순), `pacemate`·`password`·`passw0rd` 포함(대소문자·흔한 치환 `0→o, 1→i/l, @→a, $→s` 무시).
- 예시 시험: `Password1!`, `P@ssw0rd1`, `Qwer1234!`, `Abcd1234!`, `Pacemate1!` → 거부. `Tb7#kq2Lm` 같은 무작위형 → 통과.

### 2-4. 시도 제한 (설계 §E-2 4번)
- 로그인: **IP 당 실패 5회/10분** 넘으면 그 IP 를 10분 차단(429 `TOO_MANY_ATTEMPTS`, "잠시 후 다시 시도해 주세요."). **전체 실패 30회/10분** 넘으면 로그인 전체를 15분 멈춤(같은 429). 멈춤이 일어나면 경고 로그 1줄(건수만, IP·암호 없음).
- 등록·변경: UID 당 5회/시간, IP 당 10회/시간(겹침 확인을 반복해 남의 암호를 찾는 것을 막는다).
- IP 는 Render 에서는 `X-Forwarded-For` 의 **가장 오른쪽 값**(Render 프록시가 붙인 값), 그 밖에서는 `request.client.host`. 이 선택을 보고서에 적는다(PM 이 배포 후 확인). **IP 를 로그·저장소에 남기지 않는다**(메모리 카운터만, 만료 후 삭제).
- 메모리 카운터는 서버 재시작 시 초기화된다(Render 단일 인스턴스 기준, 한계로 보고). 시계는 `clock.py` 를 쓴다.

### 2-5. 삭제·관리자
- `POST /api/user/delete-data` 가 이 UID 의 `credentials` 문서를 함께 지운다(삭제 응답의 삭제 목록에도 표시).
- 관리자 [사용자 관리]에 `password_enabled` 를 보여 줄지는 **하지 않는다**(이번 범위 밖).

## 3. 프론트엔드
**화면 형태:** 목업(`mockup/index.html`)에는 이 화면이 없다. **[내 정보·설정]의 기존 카드(`FeedbackCard`, `DeleteDataSection`, `AccountIdCard`)와 동의 창(`ConsentModal`)의 스타일·간격·버튼 모양을 그대로 따른다.** 보고서에 기존 카드와 나란히 놓은 비교표(요소 순서, 스타일 클래스)를 넣는다. 목업은 PM 이 검증 후 맞춘다.

### 3-1. [내 정보·설정] "다른 기기에서 이어 쓰기" 카드 (`password_login_enabled` 일 때만)
- **등록 전:** 설명("암호를 등록하면 다른 PC·휴대폰에서 암호만으로 이 학습 기록을 이어 쓸 수 있어요"), 암호·암호 확인 입력(`type="password"`, `autocomplete="new-password"`, 레이블 있음), 규칙 안내와 입력 중 규칙 충족 표시(8자, 영문, 숫자, 특수문자 — 색만으로 표시하지 않고 글자로도), **확인 체크박스**: "암호를 잊으면 되찾을 수 없고, 이 암호를 아는 사람은 내 학습 기록을 볼 수 있다는 것을 이해했어요. 다른 사이트에서 쓰는 암호는 쓰지 않을게요." 체크해야 [등록] 활성.
- **등록 후:** "등록됨(날짜)", [암호 바꾸기](같은 입력 폼), [암호 로그인 끄기](확인 후 DELETE), [로그아웃](공용 PC 용, 확인 문구: "로그아웃하면 이 기기에서는 암호로 다시 들어와야 해요").
- 등록 전에는 로그아웃 버튼을 보여 주지 않는다(익명 상태에서 로그아웃하면 기록에 다시 들어올 수 없다).
- 저장 중 중복 클릭 방지, 성공·실패 표시, 409 는 서버 문장 그대로, 429 는 "잠시 후 다시 시도해 주세요". 쓰기는 자동 재시도하지 않는다.

### 3-2. 새 기기에서 암호로 로그인
- `ConsentModal` 아래쪽에 링크 "이미 암호를 등록했어요(사용자 인증)". 누르면 같은 창 안에서 암호 입력 폼(`autocomplete="current-password"`) → `POST /api/auth/password/login` → `signInWithCustomToken`(dev 모드는 UID 저장) → 기존 세션 복원 흐름으로 앱 진입. 이 경로에서 `signInAnonymously` 를 부르지 않는다.
- 이 UID 의 동의가 현재 약관 버전이면 동의 창을 다시 띄우지 않는다. 버전이 다르면 기존 재동의 흐름을 따른다.
- 실패 401 "암호가 맞지 않아요.", 429 "잠시 후 다시 시도해 주세요.", 꺼짐(404)일 때는 링크 자체가 없다.

### 3-3. 이미 익명 기록이 있는 기기에서 다른 기록으로 들어가기 (충돌 규칙, 설계 §5)
- [내 정보·설정] 카드에 "다른 기기에서 등록한 암호로 로그인" 링크. 누르면 경고: "지금 이 기기의 학습 기록은 암호를 등록하지 않았다면 다시 볼 수 없어요. 계속할까요?" (현재 UID 에 암호가 있으면 "지금 기록은 이 암호로 다시 들어올 수 있어요"). 계속하면 3-2 와 같은 폼. **두 기록을 합치지 않는다.**

### 3-4. 공통
- `session.ts` 에 `signInWithPassword(customToken)` 류 함수를 추가하고 dev/firebase 두 모드를 지원한다.
- 암호 값은 컴포넌트 상태에만 두고 전송 후 지운다. `wizardStorage` 같은 저장소에 넣지 않는다.
- 모바일 폭에서 카드와 폼이 깨지지 않는다.

## 4. 계약·문서 (해당 항목만)
- `backend/schemas.py`(요청·응답·오류 코드), `docs/phase1_design.md` API 표, 프론트 타입. `docs/erd_current.md` 는 컬렉션 설명 글(규칙 절)에 `credentials` 행만 추가하고 **도형은 고치지 않는다**(PM 이 검증 후 반영).
- `docs/deploy_guide.md` 에 사용자가 Render 에 넣을 값(`PASSWORD_LOGIN_ENABLED`, `AUTH_PEPPER` 생성 방법: 값은 문서에 쓰지 않고 만드는 명령만) 절을 추가한다.
- 동의 문구와 `CURRENT_TERMS_VERSION`(v1.1)은 **바꾸지 않는다.** 암호 관련 안내는 등록 카드의 확인 체크박스로 받는다(PM 판단, 사용자 확인 중).

## 5. 시험 (pytest·프론트 시험, 각 항목을 보고서 표로)
1. 꺼짐(기본): 새 API 404, `/health` false, 기존 테스트 전부 통과.
2. 등록 → 다른 "기기"(토큰 없음)에서 로그인 → 받은 토큰의 UID 가 원래 UID 와 같음 → 그 토큰으로 기존 목표·기록 조회 가능.
3. 규칙: 7자, 영문 없음, 숫자 없음, 특수문자 없음, 공백, 한글, 65자 → 422. 흔한 암호·패턴(§2-3 예시) → 409 같은 문장.
4. 겹침: A 가 쓰는 암호를 B 가 등록 → 409, 메시지가 흔한 암호 거부와 **글자 하나까지 같음**. B 의 데이터·A 의 키 불변.
5. 변경: 바꾼 뒤 옛 암호 로그인 401, 새 암호 200. 끄기 뒤 로그인 401, `password_enabled=false`.
6. 멱등: 같은 `client_request_id` 등록 재시도 200, 키 문서 1개.
7. 시도 제한: 같은 IP 6번째 실패 429, 다른 IP 는 계속 가능, 전체 31번째 실패 후 모두 429, 시간이 지나면 풀림(시계 주입). 등록 제한도 같은 방식으로.
8. 로그인 실패·성공 응답 시간 차이가 고정 지연 범위 안(대략, 불안정하면 구조 시험으로 대체하고 보고).
9. 삭제: `delete-data` 뒤 그 암호 로그인 401, `credentials` 에 그 UID 문서 0개.
10. 비노출: 등록·로그인·실패·예외 경로에서 `caplog` 에 암호·키가 없음. 응답 본문에 키가 없음. users 문서에 키 필드가 없음.
11. 시작 검사: `PASSWORD_LOGIN_ENABLED=true` + `AUTH_PEPPER` 없음/31자 → 시작 거부(메시지에 값 없음).
12. 타 UID 격리: A 의 토큰으로 B 의 암호를 끄거나 바꿀 수 없음(UID 는 토큰에서만).
13. 프론트: 카드 표시 조건(꺼짐/등록 전/등록 후), 체크박스 전 버튼 비활성, 규칙 표시, 동의 창의 로그인 링크와 실패 문구, 로그인 경로에서 익명 로그인 미호출, 로그아웃 확인.

## 6. 실제 확인 (빈 포트, 끝나면 종료)
- dev 모드(`AUTH_MODE=dev STORE_BACKEND=memory PASSWORD_LOGIN_ENABLED=true AUTH_PEPPER=<테스트용 임의값>` 을 실행 시 덮어씀): 브라우저 두 개(일반 창, 시크릿 창)로 등록 → 다른 창 로그인 → 같은 학습 기록, 변경·끄기·로그아웃, 동의 창 로그인 링크.
- firebase 모드(`backend/.env` 그대로 + 위 두 변수만 덮어씀): **새로 만든 시험용 익명 사용자 하나로만** 등록 → 시크릿 창에서 암호 로그인 → `signInWithCustomToken` 으로 **같은 UID** 가 되는지 확인. 끝나면 그 사용자로 데이터 삭제를 실행해 Firestore 에 시험 흔적을 남기지 않는다. 실제 사용자 데이터를 건드리지 않는다.
- 해시 시간, 로그인 1회 응답 시간을 적는다.
