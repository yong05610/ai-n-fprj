## 0. 범례와 규칙
| 요소 | 모양·선 | 뜻 |
|---|---|---|
| 터미널 | 사각형 | **레벨 0(배경도)만** 사람·조직(학습자, 관리자). **레벨 1~3 에서는 입력 화면·조회 화면의 논리명**(사람·조직은 터미널이 될 수 없다). 외부 시스템인 AI 서비스(OpenAI)·허용 도메인 공개 웹 페이지도 터미널로 둔다 |
| 입력 화면 | 사각형 `[입력] …` | 사용자가 값을 넣거나 **시작 명령(메뉴 선택, 다시 불러오기, 앱 접속)** 을 내는 화면. 화살표는 입력 화면 → 프로세스 한 방향 |
| 조회 화면 | 사각형 `[조회] …` | 프로세스의 결과를 보여 주는 화면. 화살표는 프로세스 → 조회 화면 한 방향 |
| 입출력 점검 | | 모든 프로세스는 입력과 출력을 함께 가진다. **입력만 있고 출력이 없으면 조회 화면 터미널 누락, 출력만 있고 입력이 없으면 입력 화면 터미널 누락**으로 보고 고친다. **조건 없는 조회도 프로세스를 시작시키는 명령이 입력**이며, 결과는 조회 화면(터미널), 저장소, 다른 프로세스로 가는 데이터 흐름 중 하나로 그린다(사용자 규칙, 2026-10-27) |
| 프로세스 | 원 | 레벨 1: 모듈 4개(P1~P4). 레벨 2: 메뉴·화면·구역·버튼 이름의 프로세스, 또는 기능이 많은 모듈은 **기능의 논리 묶음**(P2). 레벨 3: 묶음을 푼 기능, 또는 AI 호출 연쇄의 단계 |
| 다른 그림의 프로세스 | **점선 원** | 이 그림 밖에 있는 프로세스. 이어지는 선만 그리고 더 이어가지 않는다 |
| 데이터 저장소 | 띠(이중선 직사각형) | 레벨 1: **논리 저장소 5개**. 레벨 2·3: 물리 컬렉션 이름과 소속 논리 저장소를 함께 표시 |
| 다른 모듈이 만드는 저장소 | **점선 띠** + `(작성: 프로세스 번호)` | 흐름도 점선으로 그린다 |
| 쓰기 | 프로세스 → 저장소 화살표 | 저장소를 편집(삭제 포함) |
| 읽기 | 레벨 1: 점선 + `◀ 읽기:` (저장소에서 왼쪽 프로세스로). 레벨 2·3: 저장소 → 프로세스 화살표 | 저장소를 참조 |
| 양방향 | 양쪽 화살표 | 읽기와 쓰기(저장소), 요청과 응답(다른 그림의 프로세스, 외부 시스템) |
| 인증 토큰 | 흐름 이름의 `(인증 토큰)` | 프론트가 보내는 모든 요청의 머리(헤더)에는 Firebase 인증 토큰이 붙고, 서버는 그 토큰에서 UID 를 정한다. 요청 본문이 없는 요청(내 정보 조회, 목록·요약 조회 등)은 **토큰이 실제 입력**이라 흐름 이름에 `(인증 토큰)` 을 적는다. `/health`(서버 깨우기)만 토큰이 없다 |
| 생략 | | 토큰 검증 단계(Firebase)와 모든 개인 데이터 API 가 먼저 하는 `users`(동의 버전) 읽기, 마지막 활동 갱신은 그림에서 생략 |

번호 규칙(사용자 지정): **레벨 0 배경도**, **레벨 1 최상위도** = P1~P4, **레벨 2 상위도** = P1.1, P1.2 …, **레벨 3 중위도** = P1.1.1 … . 이 DFD 는 레벨 3(중위도)까지만 그리며, 엄밀한 의미의 하위도는 없다(2026-10-27 사용자 정리). 레벨 2 프로세스 수: P1 = 10(메뉴), P2 = 4(논리 묶음), P3 = 7, P4 = 10. 레벨 3 은 7장: P2 묶음 4장(P2.1~P2.4), AI 호출 연쇄 3장(P3.3, P3.5, P4.3).

## 4. 레벨 2 (상위도)와 레벨 3 (중위도)
작성 규칙(사용자 지정, 2026-10-27)을 이 절 전체에 적용했다.
1. **레벨 2 = 레벨 1 프로세스 하나를 푼 그림.** 프로세스끼리 직접 흐름을 그리지 않고, **저장소를 거쳐서만** 이어진다(저장소를 거치는 통신은 실시간 연동이 아니라 따로 움직이는 시간 사건으로 본다).
2. **프로세스 이름은 메뉴·화면·화면 안의 구역·버튼 이름**이다(API 주소를 이름으로 쓰지 않는다). API 주소는 4-6 표에 둔다.
3. **다른 그림에 속한 프로세스는 점선 원**, 다른 모듈이 만드는 저장소는 **점선 띠 + `(작성: 프로세스 번호)`** 로 그리고, 이들과 이어지는 흐름은 점선으로 그린다. 점선 원에서 더 이어지는 선은 그리지 않는다.
4. **NLM 수준**이다. CRUD(조회·생성·수정·삭제)를 쪼개지 않고, 내부 함수로 분해하지 않는다. 같은 화면 기능의 조회·저장·수정·삭제 API 는 프로세스 하나로 묶는다.
5. **기능이 많아 한 장에 담기지 않는 모듈은 레벨 2 에서 기능의 논리 묶음을 프로세스로 두고, 묶음마다 레벨 3 한 장으로 푼다**(레벨 1 에서 모듈을 묶은 것과 같은 방식, 그림을 여러 장으로 쪼개지 않는다). 이 문서에서는 P2 가 해당한다(묶음 4개 → 레벨 3 4장). 그 밖의 레벨 3 은 프로세스끼리 직접 흐름이 있는 AI 호출 연쇄 세 곳(P3.3 계획 초안 생성, P3.5 튜터 질문, P4.3 AI 주제 수집)만 그렸다.
6. **터미널은 레벨 0 에서만 사람·조직이고, 레벨 1~3 에서는 입력 화면·조회 화면의 논리명이다.** 모든 프로세스가 입력과 출력을 함께 갖는지 점검한다. 조건 없는 조회도 시작 명령(메뉴 선택, 다시 불러오기, 앱 접속)을 입력 화면에서 받는다.
7. **영역 경계:** 튜터처럼 영역에 걸치는 기능은 AI 영역(P3)이 소유한다(서비스기획서 9.2). 그래서 튜터 대화 관리와 튜터용 학습 데이터 요약은 P3 에 둔다. 타이머는 서버가 상태를 가져야 하므로(사용자당 하나, 새로고침·다른 기기 복원, 서버 시각, 멱등) P2 에 둔다.

### 4-1. 레벨 2: P1 프론트엔드(사용자 UI)
P1 은 저장소와 직접 만나지 않는다. 화면이 필요한 데이터·AI 결과는 P2 의 묶음과 P3 의 프로세스(점선 원)에서 받는다. 프로세스는 메뉴(기능) 이름이고, 터미널은 그 메뉴의 입력 화면·조회 화면이다(입력·조회 항목은 화면 코드에서 확인). 메뉴를 여는 것 자체가 조회 명령이라 입력 화면의 흐름에 "메뉴 선택"을 넣었다.

```mermaid
%%{init: {"flowchart": {"curve": "basis"}}}%%
```

### 4-2. 레벨 2: P2 백엔드(DB 인터페이스) — 논리 묶음 4개
P2 의 화면 기능 18개(+ 화면 없는 직접 편집 1개)를 **논리 묶음 4개**로 두었다. 묶음마다 레벨 3 한 장(4-5-1~4-5-4)으로 푼다. 점선 띠는 P2 가 만들지 않는 저장소다. 계획 초안(P3.3)은 저장하지 않고, 사용자가 확정할 때 P2.2(P2.2.1 계획 확정)가 학습 목표와 과제를 한 번에 저장한다.

| 묶음 | 들어 있는 기능(레벨 3) | 묶은 기준 |
|---|---|---|
| P2.1 계정·동의·설정 | 동의 저장, 내 정보 조회, 학습 전환, 내 데이터 삭제, 피드백 보내기, 서버 깨우기 | 사용자 계정 단위의 정보와 설정(활성 학습 포함), 내 정보·설정 화면 |
| P2.2 학습 계획 | 계획 확정, 학습 목록·상세, 참고자료 보기, 과제 목록, 과제 완료·요일 변경, (목표·과제 직접 편집: 화면 없음) | 학습 PLAN(`goals`, `tasks`)을 만들고 보고 고치는 기능 |
| P2.3 학습 기록 | 학습 기록 관리, 타이머 | 학습 DATA(`study_logs`, `reflections`)를 만드는 기능. 타이머는 종료 때 기록을 만든다 |
| P2.4 학습 현황·분석 | 대시보드 요약, 종합 학습 분석 조회, 인사이트 카드 조회 | 여러 저장소를 읽어 집계만 하는 조회 기능(쓰기 없음) |
