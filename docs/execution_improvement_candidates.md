# 학습 실행 화면 개선 후보 (PM 정리)

작성: PM, 2026-11-10. 상태: **후보 목록(결정 전)**. 사용자가 변경관리내역서의 "학습실행기록" 항목을 번호로 적으면, 이 목록과 합쳐 번호별로 분석하고 CR 로 만든다. 여기 있는 것은 PM 이 코드 읽기와 기존 기록에서 찾은 것이며 사용자 판단이 우선한다.

근거 코드: `frontend/components/ExecutionScreen.tsx`(학습 실행 기록 화면), `backend/main.py` `GET /api/tasks`.

### E-1 확인 결과 (PM, 2026-11-10, 코드·목업 대조)
- **결함 확정(코드 읽기).** `ExecutionScreen.tsx:324` 분모 = 활성 학습의 **전체 과제** `estimated_minutes` 합. 화면은 `주 목표 N분`이라 부르지만 실제는 "학습 전체 계획 분량"이다.
- **설계 의도와 어긋남.** 목업(`mockup/index.html`)의 실행 화면은 `주 목표 420분`(= 주 7시간 × 60)이고 달성률 = 이번 주 학습 / 420. 대시보드 API 도 `weekly_target_minutes = goal["weekly_hours"] * 60`(`main.py:1699`)을 이미 돌려준다. 즉 두 화면의 "주 목표"가 서로 다른 값이 된다.
- **부수 결함:** 기간을 "전체 기간"으로 바꾸면 분자(모든 기록)와 분모(전체 과제)가 되어 "주간 목표 달성"이라는 이름과 맞지 않는다(분모 표시는 "전체 기간"으로 바뀌지만 % 카드는 그대로).
- **과제의 `plan_week_start` 로 "이번 주 계획 합"을 만들면 안 되는 이유:** 과제가 여러 주에 걸칠 수 있다(`schedule.tasks_in_week`, 타임라인 분 단위 배치). 정확한 주간 계획 분량은 대시보드가 이미 쓰는 `week_scheduled_minutes` 방식이 맞다.
- **PM 권장:** 분모 = `weekly_hours × 60`(대시보드와 같은 값, 목업과 일치). 이번 주 계획 분량은 보조 문구로 따로 보여 줄 수 있다. 프론트가 `goals` 의 `weekly_hours` 를 이미 갖고 있는지는 개발 지시 전에 확인한다.
- 미검증: 브라우저 화면 재현(코드·목업 근거만).
- 기준값 재확인: pytest 1370, npm test 237 통과.

## 3. 제안 순서
1. **E-1 확인**(PM 이 dev 모드에서 화면 값으로 재현) → 사용자 결정(분모 기준) → CR.
