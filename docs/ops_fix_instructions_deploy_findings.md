## 2. 서버가 잠든 동안 열려 있던 화면이 "학습 계획이 없다"로 보이는 문제 (필수)
**관찰(사용자, 배포 사이트, 2026-10-25):** 탭을 연 채 약 30분 방치 → 메뉴 클릭 → 30~40초 걸림 → 화면에 "학습 계획이 없다"고 표시 → 다른 메뉴로 갔다가 오니 계획이 정상 표시됨. 계획은 저장돼 있었으므로 **화면이 사실과 다른 "빈 상태"를 보여 준 것**이다. 테스터가 새로 계획을 만들거나 데이터가 사라졌다고 믿을 수 있다.
**PM 추정(미확인):** Phase 7 의 ServerGate 는 앱을 처음 열 때만 `/health` 를 기다린다. 탭이 이미 열려 있으면 이후 API 요청이 잠든 서버로 바로 가서 실패하거나 오래 걸리고, 그 실패나 빈 응답이 "빈 상태"로 렌더된다. **원인은 코드를 읽고 재현해서 확정한다. 추정이 틀리면 알려 준다.**

### 요구
1. **먼저 원인 확인**: 어떤 요청이 어떤 경우에 빈 상태 문구를 만드는지(학습 계획 화면의 해당 분기, `lib/api.ts` 의 오류 처리, 타임아웃·재시도) 코드로 찾아 보고서에 쓴다. 가능하면 로컬에서 재현한다(예: 열린 화면에서 백엔드를 끄거나 응답을 20초 지연시킨 뒤 메뉴 이동).
2. **오류와 빈 상태를 구분**: 네트워크 실패, 타임아웃, 5xx 는 **어떤 화면에서도 "없다/비었다" 문구로 보이지 않는다.** 오류 안내 + 다시 시도로 보여 준다(기존 화면 오류 패턴 재사용).
3. **서버 깨어나는 중 안내**: 열린 상태에서도 요청이 일정 시간(예: 8초) 넘게 걸리거나 연결 오류가 나면 기존 문구 "서버를 준비하고 있습니다. 잠시만 기다려 주세요." 를 보이고, 자동 재시도(2/4/8초 간격, 총 90초 이내)한다. 입력 중인 내용은 보존한다. **쓰기 요청은 재시도해도 같은 client_request_id 를 쓴다**(중복 저장 방지). 쓰기 요청의 재시도가 위험하면 읽기 요청(GET)부터 적용하고 쓰기는 오류 안내 + 수동 재시도로 둔다. 어느 쪽인지 보고서에 쓴다.
4. 새로 만드는 것은 최소로 한다. 기존 ServerGate 의 타이머·순수 함수(`lib/coldStart.ts`)를 재사용하고, 전역 요청 래퍼(`lib/api.ts`) 한 곳에서 처리하는 방안을 먼저 검토한다.
5. 하지 않는 것: 서버 쪽 변경, 유료 플랜 전환, 주기적 핑으로 서버를 깨워 두는 방식(별도 결정 사항).

### 테스트와 검증 기준
- frontend: 요청 실패·지연·성공 순서에 따른 화면 상태(오류 ≠ 빈 상태)를 순수 함수나 컴포넌트 테스트로 확인. 기존 152건 통과, typecheck, build 통과.
- 브라우저: 백엔드를 지연/중단한 상태에서 열린 화면의 메뉴 이동 시 "없다"가 아니라 준비 안내 또는 오류+재시도가 보이고, 서버가 돌아오면 정상 데이터가 보이는 것을 보고한다(화면 확인 결과만, 원문 없이).
- PM 재검증: 배포 후 30분 방치로 같은 현상을 다시 확인한다.
