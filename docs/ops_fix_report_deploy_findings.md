## 1. 대시보드 구역 순서
- `Dashboard.tsx` 의 JSX 블록 순서를 바꿨다: 헤딩 → 종합 학습 현황 → 통계 카드 4개(또는 "최근 학습이 선택되어 있지 않아요" 블록) → 오늘의 추천 과제/오른쪽 열. 안내 문구는 "아래 통계는 최근 학습 기준이고, 이 영역은 진행 중인 전체 학습을 보여줘요."로 바꿨다. 기능·API·데이터는 그대로.
- 목업과 나란히 비교(실제 Chrome 1440×900, 목업은 file:///, 앱은 확정 계획이 있는 dev 상태):
| 항목 | 목업 | 앱 |
|---|---|---|
| 순서(위→아래) | 헤딩, 종합 학습 현황, 통계 4개, 두 열 | 같음 |
| 종합 현황 안내 문구 | "아래 통계는 …보여줘요." | 같은 문구(문자열 일치) |
| 종합 현황 → 통계 간격 | 14px | 14px |
| 통계 → 두 열 간격 | 15px | 15px |
- 위 값은 DOM 좌표 비교다. 목표 1개뿐인 상태라 종합 구역 높이는 목업(2개)과 다르다. "최근 학습이 선택되어 있지 않아요" 블록이 종합 구역 아래에 오는 배치는 코드 순서로만 확인했다(**브라우저 미검증**: 이 상태를 만들지 않았다).

## 2. 서버가 잠든 동안 열려 있던 화면이 "학습 계획이 없다"로 보이는 문제
### 원인 확인 (코드 + 로컬 재현)
- 학습 과제 계획 화면은 학습 목록(`GET /api/goals`, `GET /api/user/profile`)을 `useGoalSwitch` 훅으로 읽는다. 이 훅의 `load` 가 **실패하면 오류를 삼키고 `goals=[]`, `loaded=true`** 로 두었다("위젯은 편의 기능"이라는 주석). 화면은 `loaded` 이고 활성 학습이 하나도 없으면 "**진행 중인 학습이 없어요** — 학습 경로를 만들면…" 빈 상태를 그린다. 즉 **목록을 못 읽은 것이 "비어 있음"으로 둔갑**했다. 메뉴를 다시 열면 요청이 성공해서 정상 표시됐다(사용자 관찰과 일치).
- `lib/api.ts` 는 실패를 `NETWORK_ERROR`/`REQUEST_TIMEOUT`/상태 코드 오류로 정직하게 던지고 있었다. 문제는 그 오류를 받는 쪽이다. 추가로 연결 실패는 GET 이든 아니든 한 번 시도하고 끝이라 잠든 서버(30~60초)를 기다려 주지 않았다.
- **재현**(수정 전 코드, 열린 앱에서 `/api/**` 호출을 연결 실패로 만든 뒤 대시보드 → 학습 과제 계획 메뉴 이동): 화면에 "진행 중인 학습이 없어요"가 나타났다(확인). 같은 시나리오가 수정 후에는 아래 결과다.
- 같은 분기가 다른 화면에도 있는지(목록):
| 화면 | 읽기 실패 처리 | 판정 |
|---|---|---|
| 대시보드 | 오류 문구 + "다시 시도"(상태 `error`) | 정상(빈 상태와 구분됨) |
| 학습 실행 기록 | 오류 문구 + 오류 상태(`loadStatus: error`) | 정상 |
| 종합 학습 분석 | 오류 문구 + 오류 상태 | 정상 |
| AI 튜터 — 대화 목록 | `listError` 표시 | 정상 |
| AI 튜터 — 오른쪽 학습 요약 | 실패를 삼키고 "…불러오는 중이거나 아직 없어요" | **같은 종류**(덜 심함: "없어요"라고 단정하지는 않음). 수정함 |
| 인사이트 카드 | "저장된 인사이트를 불러오지 못했어요" 알림 | 정상 |
| 학습 경로 설정(위저드)의 "현재 학습" 위젯 | 실패하면 위젯이 사라짐(빈 상태 문구는 없음) | 문구상 문제 없음. 훅은 같은 것이라 이제 `loadFailed` 를 가진다 |
| 학습 과제 계획 | 위 원인 | **수정함** |

### 수정 내용
| 항목 | 내용 | 파일 |
|---|---|---|
| 오류 ≠ 빈 상태 | `useGoalSwitch` 가 `loadFailed` 와 `reload` 를 노출. 재시도 시 `loaded=false` 로 돌려 "없어요"가 깜빡이지 않게 함. 학습 과제 계획 화면은 순수 함수 `learningListView(loaded, loadFailed, 활성 개수)` 로 `loading/error/none/some` 을 정하고 `error` 에서는 "학습 목록을 불러오지 못했어요. 잠시 후 다시 시도해 주세요." + "다시 시도" 를 보인다(기존 오류 카드 패턴). 튜터의 학습 요약은 실패 시 "학습 요약을 불러오지 못했어요. 다시 시도" | `useGoalSwitch.ts`, `WeeklyPlanScreen.tsx`, `lib/weekPlan.ts`, `TutorScreen.tsx` |
| 깨어나는 중 안내와 자동 재시도 | **전역 요청 래퍼 한 곳**(`lib/api.ts`)에서 처리. GET 이 연결 실패/타임아웃/502·503·504 로 끝나면 2초·4초·8초(이후 8초) 간격으로 다시 보내고, 총 90초까지 기다린다. 요청이 8초 넘게 열려 있거나 첫 실패가 나면 기존 문구 "서버를 준비하고 있습니다. 잠시만 기다려 주세요." 띠를 화면 위에 보이고, 끝나면 사라진다. 90초 후에도 실패하면 오류를 화면에 넘겨 각 화면의 오류 + 다시 시도가 나온다. 그 밖의 오류(400, 401, 403, 404, 409, 500 등)는 진짜 응답이라 재시도하지 않는다 | `lib/api.ts`, `lib/wakeRetry.ts`(새), `lib/coldStart.ts`(`isWakeFailure` 추가, 기존 간격 함수 재사용), `lib/serverWake.ts`(새), `components/WakeNotice.tsx`(새), `app/layout.tsx` |
- **쓰기 요청은 자동 재시도하지 않는다(GET 만 적용).** 이유: 쓰기 중 `client_request_id` 가 없는 것(과제 수정, 타이머 시작·종료, 학습 기록, 프로필 수정, 삭제 등)이 있어 자동으로 다시 보내면 중복 저장이나 의도치 않은 두 번째 실행이 될 수 있다. 쓰기가 실패하면 기존대로 각 화면의 오류 안내가 나오고 사용자가 직접 다시 시도한다. AI 쓰기(튜터 질문, 인사이트 생성, 계획 확정)는 기존대로 같은 `client_request_id` 를 보존해 수동 재시도해도 중복되지 않는다(변경 없음). 입력 중인 내용은 쓰기 실패 때 지워지지 않는다(기존 규칙, 변경 없음).
- 앱을 처음 여는 경우는 기존 ServerGate 가 그대로 담당하고(대기 중 다른 요청 없음), 이번 띠는 이미 열린 앱에서만 나온다. 두 띠가 동시에 보이는 일은 없다(게이트가 앱을 그리지 않는 동안에는 래퍼 요청이 없음).

## 미검증
- 실제 배포(Render 무료 서버가 잠든 뒤)에서의 동작. 연결 실패가 아니라 서버가 30~60초 뒤에 502/503 을 돌려주는 경우도 재시도 대상이지만 이번에는 502/503 응답 자체를 만들어 보지 않았다(분류는 단위 테스트로만).
- 학습 실행 기록, 대시보드, 종합 분석 화면의 같은 시나리오(코드상 각 화면이 오류 상태를 가짐을 확인했고, 브라우저로는 학습 과제 계획만 확인).
- 대시보드 "최근 학습이 선택되어 있지 않아요" 상태의 순서, 모바일 폭.

## 열린 결정
1. GET 재시도가 90초까지 이어지므로, 서버가 정말 죽은 경우 화면은 최대 90초 뒤에야 오류를 보인다(그동안 상단 띠로 안내). 다른 화면으로 옮겨도 이전 요청의 재시도는 끝까지 간다(결과는 무시됨).
2. 쓰기 요청의 자동 재시도는 `client_request_id` 를 모든 쓰기에 도입한 뒤에야 안전하다. 필요하면 별도 지시.
