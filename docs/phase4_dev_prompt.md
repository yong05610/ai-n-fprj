# Phase 4 개발팀 착수 프롬프트 (PLAN · AI 학습 경로·계획)

아래 전체를 개발팀(Backend/Frontend)에게 그대로 전달한다. 표 없이 목록으로만 작성했다.

---

## 역할과 목표

너는 PaceMate 개발팀이다. TASK.md의 **Phase 4 (4.1~4.6)만** 구현한다.
목표: 분야 자유 입력 → AI가 세부 과정·과정별 수준 제안 → 사용자가 과정·현재/목표 수준 선택 → AI 주간 계획 초안 → 사용자가 편집·확정 → Firestore 저장·재조회.

기준 문서: PRD.md FR-02, TASK.md Phase 4, docs/erd_current.md, docs/phase3_review_instructions.md, mockup/index.html(page-path, page-wbs 화면)

## 진행 규칙 (반드시 지킨다)

1. Phase 4 범위만 구현한다. Phase 5(학습 기록·타이머·대시보드)와 Phase 6(튜터·RAG 검색)은 스키마든 뼈대든 앞서 만들지 않는다.
2. 끝나면 실행 결과(테스트 출력, 완료한 Task 번호, 미완료, 사용자 조치 필요, 열린 결정)를 보고하고 **멈춘다.** 검증팀 검증과 사용자 지시 후에만 다음 Phase로 간다.
3. 실제 비밀값(OpenAI 키, Firebase 서비스 계정)을 코드, 로그, 채팅, 커밋에 남기지 않는다.
4. TASK.md 체크박스는 직접 검증한 항목만 체크한다. 실제 OpenAI나 Firebase 연동으로 확인하지 못한 것은 "미검증"이라고 적는다.

## 착수 전 정리 (Phase 4 코드보다 먼저)

- 아직 push되지 않은 커밋이 있으면 push 상태를 확인하고 보고한다.
- docs/ 안의 브라우저 저장 PDF 파일은 저장소에 올리지 않는다(삭제하거나 밖으로 옮긴다).
- 문서 기준을 맞춘다: PRD §6 필드명을 구현 이름(field, target_date, course, content)에 맞추고, docs/phase1_design.md의 ERD를 갱신한다(users의 active_goal_id·consent_version, goals의 수준 설명, study_logs의 started_at·ended_at, *_level_order 이름). erd_current.md 합의 사항 5번의 "미정"도 닫는다.
- 서비스 시간대를 Asia/Seoul로 확정하고, 주간 경계(월~일)와 "오늘" 판정이 서버 날짜(date.today, 배포 시 UTC)에 의존하지 않도록 공통 함수 하나로 모은다. Phase 4와 Phase 5가 같이 쓴다.

## 수준(level) 해석 원칙 (프롬프트·검증·화면 모두 적용)

- 수준은 서술형 라벨이다. 이름과 설명이 의미를 가지며 정량 지표나 표준 등급이 아니다.
- 수준 번호(order)는 같은 과정 안의 순서 등급일 뿐이다. 간격·비율·합산·다른 과정과의 비교에 쓰지 않는다.
- 화면에는 번호를 표시하지 않고 수준 이름만 표시한다. 선택한 수준의 짧은 설명만 보조 문구로 보여 준다.
- 수준표 전체는 DB에 저장하지 않는다. 목표에는 선택한 현재·목표 수준의 이름과 설명을 스냅샷으로 저장한다.

## Backend 작업

### 4.1 POST /api/path/recommend
- 인증: require_consented_uid 적용(동의 전 403, 토큰 없음 401).
- 입력: field(필수), goal(선택), user_context(선택). 길이 제한을 두고 공백만 있는 값은 거부한다.
- 출력: courses[](id, title, description, levels[](order, name, description)), suggested_roles(최대 5개).
- LLM 응답을 Pydantic으로 검증한다. 검증 항목: 과정 1개 이상, 과정별 수준 1개 이상, order가 과정 안에서 중복 없이 오름차순, 이름·설명 비어 있지 않음, 직무명 5개 이하. 분야 목록을 하드코딩하지 않는다.
- 응답에 DB ID를 요구하지 않는다. 과정 id는 서버가 슬러그로 부여해도 된다.
- 이 단계에서는 아무 데이터도 저장하지 않는다.

### 4.3~4.4 POST /api/plan/generate
- 입력 계약 결정을 먼저 해결한다(아래 "열린 결정 1" 참고). 최종 입력에는 field, course(목표당 1개), selected_role(선택), 현재·목표 수준(이름, 설명, 순서), weekly_hours, target_date, plan_week_start(기본: 서비스 시간대 기준 이번 주 월요일)가 필요하다.
- 서버 검증: 목표 수준 order가 현재보다 커야 한다(같으면 거부). plan_week_start는 월요일이어야 한다. 주간 범위가 target_date를 넘는 주간은 생성하지 않는다. target_date는 오늘 이후여야 한다.
- LLM 응답 검증: 주간 시작·종료일, 과업 배열(title, description, estimated_minutes, 선택적 suggested_weekday). 총 예상 시간이 weekly_hours×60분을 넘으면 거부하거나 서버에서 보정하지 말고 재시도 후 오류로 처리한다(조용히 잘라내지 않는다). suggested_weekday는 none, mon~sun만 허용한다.
- 서버가 task ID, 기본 상태(pending), order_index를 부여한다. AI 응답에는 ID를 요구하지 않는다.
- 응답은 주간 과업 목록, 조언(advice), 참고자료(references)를 각각 독립 데이터로 반환한다.
- 참고자료는 backend/data/rag_documents.json의 검토된 자료에서만 고른다. 자료가 없는 분야면 references를 비우거나 "자료 미확보" 표시를 하고, RAG 근거가 있는 것처럼 표현하지 않는다. 확인용 검색 키워드를 제안한다(docs/phase2_prep.md의 문구 참고).
- 이 호출은 계획 **초안만** 반환한다. 초안은 확정 전까지 저장하지 않는다.

### 4.5 계획 확정·저장
- 사용자가 편집한 최종 계획을 저장하는 API를 만든다(열린 결정 1의 방식에 맞춘다). 저장은 하나의 요청 안에서 원자적으로 처리하거나, 실패 시 부분 저장이 남지 않게 한다.
- 저장 시 서버가 다시 검증한다(월요일 주간, 시간 총량, target_date 범위, 길이 제한, 공백, 요일 값). 클라이언트가 보낸 user_id는 무시한다.
- 기존 POST /api/tasks도 같은 검증 규칙을 쓴다(AI를 거치지 않는 저장 경로가 규칙을 우회하지 않게 한다). 검증 함수를 한 곳에 두고 공유한다.
- 저장 후 GET /api/tasks?goal_id=&plan_week_start= 로 재조회되어야 한다.
- 추천 요일은 마감일이 아니다. 지나가도 과제를 실패나 이월 처리하지 않는다. 사용자가 다른 요일로 바꾸거나 none으로 둘 수 있어야 한다.

### 4.6 AI 호출 공통 처리
- OPENAI_API_KEY와 모델명은 환경변수로 받는다(backend/.env.example에 이름만 추가, 값은 넣지 않는다).
- 호출은 별도 모듈(예: ai_client.py)로 분리해 테스트에서 가짜 클라이언트로 바꿀 수 있게 한다.
- 타임아웃과 제한된 재시도(예: 최대 2회)를 둔다. 스키마 파싱 실패와 타임아웃은 서로 다른 오류 코드로 구분한다(예: AI_SCHEMA_ERROR 502, AI_TIMEOUT 504, AI_UNAVAILABLE 503). 오류 응답은 기존 ErrorResponse 형식을 지킨다.
- 로그에는 오류 유형만 남긴다. 사용자 입력 원문, 프롬프트, AI 응답 원문, 토큰을 남기지 않는다.
- 사용자 입력은 프롬프트 안에서 데이터로만 취급한다(지시문으로 해석되지 않게 구분자와 시스템 지시를 분리). 입력 길이와 출력 토큰 상한을 둔다.
- 사용자당 단순 호출 제한(비용·남용 방지)을 둘지 검토하고, 안 한다면 이유를 문서에 적는다.
- 모든 AI 생성 응답에 "AI가 생성한 내용이며 정확성을 확인해 주세요" 안내 문구를 담을 수 있게 한다(프론트가 표시).

## Frontend 작업

### 4.2 학습 경로 설정 화면 (mockup page-path 기준)
- 분야 입력 폼(자유 입력), 목표 입력(선택), 추천 실행 버튼, 재시도 버튼.
- 과정 Chip 선택. 직무명 추천(최대 5개) 선택. 사용자가 과정·수준 이름을 수정하거나 다시 생성할 수 있다. 다시 생성해도 입력값과 선택은 유지한다.
- 현재 수준·목표 수준 콤보박스는 선택한 과정의 수준 이름으로 동적으로 채운다. 번호는 표시하지 않는다. 선택한 수준의 짧은 설명만 보조 문구로 표시한다. 목표 수준은 현재 수준보다 뒤인 항목만 선택 가능하다. 별도의 단계 카드나 번호 목록을 만들지 않는다.
- 목표 완료일, 주당 학습 가능 시간, 계획 주간(기본 이번 주, 변경 가능)을 입력한다.

### 4.5 계획 화면 (mockup page-wbs 기준)
- 탭 3개: 주간 과업, 조언, 참고자료. 각각 독립 데이터로 렌더링한다.
- 주간 범위 선택, 과업 제목·설명·예상 시간 편집, 추천 요일 변경(none 포함), 과업 추가·삭제.
- 총 예상 시간이 주당 가능 시간을 넘으면 확정 전에 화면에서 경고하고 확정을 막는다(서버 검증과 별도로).
- 확정 버튼 → 저장 중 → 저장 완료/오류 표시 → 재조회로 저장된 내용 확인. 확정 전 초안은 새로고침이나 오류 후에도 보존한다.
- 화면에 "추천 요일은 마감일이 아닙니다" 취지의 안내를 둔다. AI 생성 안내 문구를 표시한다. 자료가 없는 분야는 "등록된 검토 자료가 없습니다"와 검색 키워드 제안을 보여 준다.

### 4.6 상태 처리
- 단계별 상태를 정의한다: 입력, 선택, 요청 중, 성공, 오류. 요청 중에는 중복 제출을 막는다.
- AI 스키마 오류와 타임아웃에서는 사용자가 입력한 분야, 선택 조건, 편집 중인 계획을 보존하고 해당 단계만 재시도할 수 있게 한다. 오류 코드별 안내 문구를 다르게 보여 준다.
- apiRequest에 타임아웃과 재시도 정책을 도입한다(Render 첫 요청 지연에 대비해 "서버를 준비하고 있습니다" 안내까지는 Phase 7이지만, 요청이 무한 대기하지 않게 한다).
- 동의 전에는 이 화면에 진입시키지 않는다(기존 AuthProvider 흐름 유지).

## 열린 결정 (구현 전에 정하고 문서화해서 보고)

1. **확정 전 저장 문제.** 지금 PlanGenerateRequest는 사전에 만든 goal_id를 요구한다. 그러면 계획을 확정하기 전에 목표 문서가 먼저 저장되어 "확정한 과정·수준·계획만 저장"(PRD FR-02)에 어긋난다. 권장안: plan/generate는 goal_id 없이 선택 조건을 받아 초안만 반환하고, 확정 API 한 번으로 목표와 과제를 함께 저장한다. 다른 방식을 택하면 이유를 적고 DTO와 erd_current.md를 함께 갱신한다. 이 변경은 Frontend와 Backend가 같이 합의한다.
2. 한 사용자의 목표 개수와 active_goal_id 처리(새 목표 확정 시 기존 목표를 어떻게 할지).
3. 같은 목표·같은 주간에 계획을 다시 확정할 때의 동작(덮어쓰기, 추가 금지, 기존 과제 보존 등).
4. 수준 order 상한(현재 1~20)과 과정·수준 개수 상한을 프롬프트와 검증에 맞춘다.

## 테스트 요구사항

- 실제 OpenAI 호출 없이 통과하는 단위·계약 테스트를 만든다(가짜 AI 클라이언트 사용).
- Backend: 정상 경로, 스키마 위반 응답 거부, 타임아웃과 재시도, 수준 순서 위반(같은 수준 포함), 시간 총량 초과, target_date 초과 주간, 월요일이 아닌 주간 시작, 허용되지 않는 요일 값, UID 격리(타 UID가 저장한 계획 접근 불가), 동의 전 403, 토큰 없음 401, 로그에 원문이 남지 않음, 자료 없는 분야의 응답 표시.
- Frontend: typecheck와 build 통과. 단계별 상태 전환, 오류 후 입력 보존, 목표 수준 선택 제한은 가능한 범위에서 테스트한다.
- 실제 OpenAI 키가 있을 때만 쓰는 선택적 스모크 테스트를 분리하고, 키가 없으면 건너뛴다. 실행하지 못했다면 보고서에 "실 LLM 미검증"이라고 적는다.

## 완료 기준 (TASK.md Phase 4)

- 분야 목록을 하드코딩하지 않고 과정·수준 제안부터 주간 계획 확정·저장·재조회까지 동작한다.
- 총 예상 시간이 주간 가능 시간을 초과하지 않는다.
- 사용자가 추천 요일을 바꾸거나 추천 없이 과제를 둘 수 있다.
- 미인증과 타 UID 접근은 거부된다.
