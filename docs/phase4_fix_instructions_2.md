# Phase 4 수정 지시서 2 — 실제 OpenAI 호출 스모크 결과 (P4-8, P4-9)

작성: 검증팀. 표 없이 목록으로만 작성했다.
배경: 실제 OpenAI 키(gpt-4o-mini, 기본 모델)로 처음 호출해 본 결과다. 자동 테스트는 가짜 AI를 쓰기 때문에 이 결함들을 잡지 못했다.
전제: 이 수정만 한다. Phase 5는 사용자 지시 전까지 시작하지 않는다. 수정 후 보고하고 멈춘다.

---

## 확인된 사실 (재현 결과)

- POST /api/path/recommend 는 200, 약 7~8초. 과정 5개와 직무 5개를 한국어로 생성한다.
- 그러나 5개 과정 모두 levels 가 1개뿐이었다(예: "입문자"만). 목표 수준 선택지가 비어 사용자가 진행할 수 없다.
- POST /api/plan/generate 는 같은 입력으로 3회 호출했을 때 estimated_minutes 합계가 660분, 570분, 420분(한도 360분)으로 나왔다. 서버는 규칙대로 거부했고, 3회 재시도가 모두 실패해 502 AI_SCHEMA_ERROR 가 되었다. 사실상 계획 생성이 항상 실패한다.
- 해결책 사전 검증: 입력에 max_total_minutes(=weekly_hours*60)를 직접 주고 "합계는 이 값 이하" 규칙을 프롬프트에 추가하자 5회 모두 통과했다(300~360분).

## P4-8. 과정당 수준이 1개뿐이다 (높음)

### 원인
- backend/prompts.py 의 PATH_RECOMMEND_SYSTEM_PROMPT 가 "수준을 1개 이상 20개 이하"라고 한다. 모델이 최소값 1개를 택한다.
- backend/ai_schemas.py 의 AICourseItem.levels 와 backend/main.py 의 _validate_ai_path 도 최소 1개만 요구한다.

### 수정
1. 프롬프트: 과정마다 수준을 최소 3개, 최대 6개로 만들라고 명시한다. 수준은 같은 과정 안에서 쉬운 것부터 어려운 것 순서로, 서로 구별되는 서술형 이름과 설명을 가져야 한다고 쓴다. 이름에 숫자나 "1단계"를 쓰지 않는다는 기존 규칙은 유지한다.
2. 검증: AICourseItem.levels 의 최소 개수를 2로 올리고(목표 수준 선택이 가능한 최소), _validate_ai_path 에서 과정당 수준이 2개 미만이면 거부해 재시도로 넘어가게 한다. 프롬프트 권장은 3~6이지만 검증은 최소 2로 둔다.
3. 공개 응답 DTO(CourseItem.levels)의 최소 개수도 일관되게 맞춘다. 단일 수준만 있는 과정이 응답에 나오지 않게 한다.
4. 프론트의 "수준이 1개뿐인 과정 차단" 가드는 유지한다(다른 경로에서 나오는 방어용).

### 테스트
- 가짜 AI가 과정 수준 1개를 반환하면 재시도 후 AI_SCHEMA_ERROR 가 되는 테스트.
- 수준 2개 이상은 통과하는 테스트.
- 서술형 이름 규칙(번호 이름 금지)은 서버가 판단하기 어려우므로 프롬프트에만 둔다.

## P4-9. 계획 생성이 시간 한도를 거의 항상 초과한다 (높음)

### 원인
- PLAN_GENERATE_SYSTEM_PROMPT 가 "weekly_hours*60(분)을 넘지 않는다"고만 쓰고, 모델이 곱셈을 직접 해야 한다. gpt-4o-mini 는 이 규칙을 지키지 못한다.

### 수정
1. backend/main.py 의 generate_plan 에서 weekly_hours*60 을 계산해 user_payload 에 max_total_minutes 로 전달한다.
2. 프롬프트에서 weekly_hours*60 계산 문구를 없애고, "max_total_minutes 이하" 규칙으로 바꾼다. 과업 개수도 3~6개 범위로 권장한다. suggested_weekday 규칙과 입력 데이터가 지시가 아니라는 문구는 그대로 둔다.
3. 재시도 개선: 시간 초과로 검증에 실패하면 다음 시도에서 이전 합계와 한도를 모델에게 알려 준다(예: user_payload 에 previous_total_minutes 와 한도 재강조 필드 추가). AIClient.generate 가 이를 지원하도록 검증 실패 사유를 다음 시도 입력에 넘길 수 있게 확장하거나, 호출 측에서 payload 를 갱신하는 방식 중 단순한 쪽을 택한다. 어느 쪽이든 로그에 사용자 입력·AI 응답 원문을 남기지 않는다.
4. 서버의 거부 정책은 유지한다. 초과 시 조용히 자르거나 보정하지 않는다.

### 테스트
- 가짜 AI가 첫 시도에 한도를 초과하고 둘째 시도에 한도 이내를 반환하면 성공하는 테스트(재시도 입력에 한도 정보가 담기는지 확인).
- user_payload 에 max_total_minutes 가 weekly_hours*60 으로 들어가는지 확인하는 테스트.
- 기존 "모든 시도가 초과면 AI_SCHEMA_ERROR" 테스트는 유지한다.

- 모델명은 환경변수(OPENAI_MODEL)로 바뀔 수 있다. 프롬프트 수정은 기본 모델 gpt-4o-mini 기준으로 실제 호출해 검증한다.
- 호출 시간: 추천 약 8초, 계획 생성은 실패 시 약 14초(3회 시도)였다. 프론트 타임아웃(70초)과 서버 시도 횟수의 관계가 이번 수정 후에도 맞는지 확인한다.
