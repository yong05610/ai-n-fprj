# Phase 5 개발팀 착수 프롬프트 (EXEC · 학습 실행·회고·진행)

아래 전체를 개발팀(Backend/Frontend)에게 그대로 전달한다.

---

## 역할과 목표

너는 PaceMate 개발팀이다. TASK.md의 **Phase 5 (5.1~5.9)만** 구현한다.
목표: 사용자가 저장된 학습 과제를 골라 학습 기록(타이머 또는 수동 입력)과 한 줄 회고를 남기고, 기록을 수정·삭제하며, 대시보드와 진행현황이 그 결과를 일관되게 보여 준다.

기준 문서: PRD.md FR-03, FR-05(저장 부분), FR-06, TASK.md Phase 5, docs/erd_current.md, docs/phase4_plan.md, mockup/index.html 의 page-dashboard 와 page-execution 섹션.

## 진행 규칙 (반드시 지킨다)

1. Phase 5 범위만 구현한다. AI 인사이트 생성(6.9), 튜터·RAG·회고 검색(6.x), 참고자료 보관함 화면은 만들지 않는다. 대시보드의 인사이트 카드는 AI를 호출하지 않는다(아래 "인사이트 카드" 참고).
2. 끝나면 실행 결과(테스트 출력, 완료한 Task 번호, 미완료, 사용자 조치 필요, 열린 결정)를 보고하고 **멈춘다.** 검증팀 검증과 사용자 지시 후에만 Phase 6으로 간다.
3. 비밀값(OpenAI 키, Firebase 서비스 계정)을 코드, 로그, 채팅, 커밋에 남기지 않는다. 키가 필요한 검증은 사용자가 backend/.env 에 넣은 값을 쓰되 값은 출력하지 않는다.
4. TASK.md 체크박스는 직접 검증한 항목만 체크한다. 브라우저에서 직접 조작해 확인하지 못한 UI는 "미검증"이라고 적는다.
5. 구현은 dev 모드(AUTH_MODE=dev, STORE_BACKEND=memory)로 진행한다. Firebase 실연동은 사용자가 콘솔 설정을 마치면 검증팀이 별도로 요청한다. Firestore 실연동을 전제로 한 가정(트랜잭션 등)을 코드에 숨기지 않는다.
6. 계약(DTO) 을 바꾸면 backend/schemas.py, docs/erd_current.md, docs/phase1_design.md, 프론트 타입을 함께 갱신한다.

## 승계 원칙 (Phase 3~4 결정, 그대로 지킨다)

- UID는 토큰에서만 결정한다. 요청 본문의 user_id 와 goal_id 같은 소유 정보는 신뢰하지 않고, 과제(task_id)로부터 서버가 goal_id 를 도출하고 소유권을 검사한다.
- 개인 데이터 API는 require_consented_uid 를 쓴다. 오류 응답은 ErrorResponse 형식.
- 수준은 서술형 라벨이다. 번호(order)는 순서 등급일 뿐 계산에 쓰지 않고 화면에 표시하지 않는다. 진행률은 완료 과제 수 / 전체 과제 수다.
- 날짜와 주간 경계는 backend/clock.py (Asia/Seoul, 월요일~일요일)와 frontend/lib/week.ts 만 쓴다. date.today(), 브라우저 로컬 날짜, toISOString 날짜 변환을 쓰지 않는다.
- 쓰기 요청에는 client_request_id 로 멱등 처리를 한다(Phase 4 plan/confirm 방식과 동일). 같은 키 재시도는 200과 기존 결과를 반환하고 중복 생성하지 않는다.
- 로그에 회고·활동 내용 원문, 토큰을 남기지 않는다.
- 삭제 전파: 기록 삭제는 그 기록의 회고도 삭제하지만 과제는 지우지 않는다(5.5). 과제 삭제는 기존대로 하위 기록·회고를 삭제한다.
- 추천 요일은 마감일이 아니다. 놓쳐도 과제를 연체·실패 처리하거나 다음 날로 자동 이동하지 않는다.

## Backend 작업

### 5.3~5.6 학습 기록 API (현재 501 스켈레톤을 실제 구현으로 교체)
- 엔드포인트: GET/POST /api/study-logs, PATCH/DELETE /api/study-logs/{log_id}. 기존 StudyLog DTO(task_id, study_date, minutes, activity, started_at, ended_at, reflection)를 출발점으로 하되 필요하면 조정한다.
- 생성: task_id 필수. 서버가 task 소유권을 검사하고 goal_id 를 task 에서 도출한다(요청의 goal_id 는 무시하거나 제거). 존재하지 않는 과제는 404, 타 UID 과제는 403.
- 한 과제에 여러 기록을 저장·조회할 수 있어야 한다(1:N).
- 검증: study_date 는 YYYY-MM-DD 이고 서비스 시간대 기준 오늘 이후(미래)가 아니어야 한다. minutes 는 1 이상이며 상한(예: 1440)을 둔다. activity 는 공백만 불가, 길이 제한. started_at/ended_at 은 둘 다 있거나 둘 다 없고, 있으면 started_at < ended_at 이어야 한다. 사용자가 시간을 직접 보정할 수 있으므로 minutes 는 started_at/ended_at 에서 자동 계산하되 사용자가 보낸 minutes 를 우선 저장한다(보정 허용). 이 규칙을 문서에 적는다.
- 회고(reflection): 기록과 함께 생성·수정할 수 있다(기록 1 : 회고 0..1). content 공백 불가·길이 제한, tags 개수·길이 제한, 중복 태그 정리. 회고만 지우는 방법(예: reflection 을 null 로 PATCH 하거나 별도 삭제)을 하나 정해 문서화한다. 현재 PATCH 는 None 값을 변경으로 취급하지 않으니(_changes 의 exclude_none) 이 부분을 정확히 처리한다.
- 목록: task_id 필터, period(week | all, 기본 week). 주간은 서비스 시간대 월~일. 정렬은 study_date 내림차순, 같은 날은 최근 생성 순. 응답에 페이지 크기 상한을 둔다(무제한 반환 금지).
- 수정·삭제: 본인 기록만. 삭제 전에 서버가 하는 일은 없고(확인은 프론트), 삭제는 회고까지 지우되 과제 상태와 다른 기록은 유지한다.
- 쓰기 동시성: 가능한 한 한 번의 요청에서 기록과 회고가 함께 저장되거나 함께 실패해야 한다. 검증을 모두 마친 뒤에 쓰고, 부분 저장 가능성이 남으면 문서에 적는다.

### 5.2 타이머 (서버 측 한 사용자 한 타이머)
- PRD FR-03: 한 사용자에게 동시에 진행 중인 타이머는 하나만 허용한다. 탭이나 기기가 달라도 지켜지도록 **서버가 활성 타이머 상태를 가진다.** 저장 위치(예: users 문서의 active_timer 필드)와 계약을 개발팀이 정하고 근거와 함께 문서화한다. 별도 컬렉션을 늘릴지, users 필드로 둘지 결정을 보고한다.
- 최소 동작: 시작(task_id, 시작 시각은 서버 시각), 종료(→ 기록 초안의 started_at/ended_at/minutes 를 돌려주고, 사용자가 활동·회고를 입력해 저장하면 study_log 가 됨), 활성 타이머 조회(새로고침 복원용), 취소.
- 이미 활성 타이머가 있는데 시작하면 409 와 코드(예: TIMER_ALREADY_RUNNING)로 거부하고, 응답에 진행 중인 과제 정보를 담아 프론트가 "먼저 종료·저장하세요"를 안내할 수 있게 한다.
- 일시정지(paused)가 TASK 5.2 상태 머신에 있다. 구현하려면 누적 시간 계산(서버 시각 기준)이 맞아야 한다. 구현 비용이 크면 일시정지는 제외하고 PRD 의 "학습 시작·종료"만 구현하되, 그 결정과 이유를 보고서에 적고 사용자 승인을 받는다(조용히 빼지 않는다).
- 타이머 시각은 서버가 정한다(클라이언트 시계를 신뢰하지 않는다). 너무 긴 활성 타이머(예: 24시간 초과)는 종료 시 거부하거나 보정 유도한다.
- 과제를 지정하지 않은 타이머 시작은 불가(5.2). 삭제된 과제의 활성 타이머는 정리한다. 데이터 삭제 요청(delete-data)이 활성 타이머까지 정리하는지 확인한다.

### 5.7 GET /api/dashboard/summary (현재 501 스켈레톤 교체)
- 한 응답으로 제공: 활성 목표 제목, 수준 진행 문구(수준 이름으로 "현재 → 목표" 문구, 번호 사용 금지), 완료 과제 수·전체 과제 수·진행률(%), 이번 주 학습 시간(분)과 주간 목표 시간(분, 목표의 weekly_hours×60), 총 학습 기록 수, 오늘의 추천 과제 목록(완료 여부, 기록 수 포함), 월~일 주간 hit 배열(날짜, 요일 라벨, 활동 여부, 오늘 여부), 인사이트 카드 데이터.
- 활성 목표는 users.active_goal_id. 없으면 빈 상태 기본값(0, 빈 목록, 7일 hit 전부 false, 인사이트 부족 안내)을 반환하고 그 기본값을 문서에 명세한다. 200 으로 반환한다(오류로 취급하지 않는다).
- 주간 경계는 서비스 시간대 월~일. 학습 시간과 기록 수는 study_date 가 이번 주인 기록만 집계한다.
- 오늘 추천 과제: 이번 주(plan_week_start 가 이번 주 월요일) 미완료 과제 중 suggested_weekday 가 오늘 요일인 과제를 우선하고, 없으면 이번 주 미완료 과제 중 다음 순서(order_index)의 과제를 보여 준다. 지난 요일의 미완료 과제를 연체로 표시하거나 오늘로 자동 이동하지 않는다.
- 진행률 분모가 0이면 0%. 소수 처리 규칙(반올림 등)을 정해 문서화한다.
- 인사이트 카드: Phase 5 에서는 AI 를 호출하지 않는다. 기록·회고가 부족하면 is_insufficient=true 와 "기록을 더 남기면 인사이트를 볼 수 있어요" 안내를, 충분하면 AI 인사이트는 Phase 6 에서 제공됨을 알리는 중립 안내만 반환한다. 가짜 AI 문장을 만들어 보여 주지 않는다. 충분/부족 기준(예: 기록 N건 이상 + 회고 M건 이상)을 정해 문서화한다.
- 성능: 요청당 쿼리 수를 줄인다(필요한 컬렉션을 user_id 기준으로 한 번씩만 읽고 파이썬에서 집계). 데이터가 커질 때를 대비한 상한을 문서에 적는다.

### 5.8~5.9 과제 완료 상태와 집계 일관성
- 과제 완료 토글은 기존 PATCH /api/tasks/{id} 의 status(pending | completed)를 쓴다. 기록 저장이 과제를 자동 완료시키는지 여부를 결정해 문서화한다(권장: 자동 완료하지 않고 사용자 토글만).
- 과제별 누적 학습 시간, 주간 기록 수·학습 시간·진행률이 기록 생성·수정·삭제와 과제 완료 토글 뒤에 모두 일관되게 갱신되어야 한다. 집계는 요청 시 계산하므로 별도 캐시 필드를 두지 않는다(두면 불일치 위험을 문서에 적는다).
- 과제 조회(GET /api/tasks)에 누적 학습 시간·기록 수를 포함할지, 별도 집계 엔드포인트를 둘지 결정한다. 화면(과제별 진행현황)에 필요한 데이터를 한 번의 요청으로 얻을 수 있어야 한다.

## Frontend 작업

### 앱 틀과 이동 (필수)
- 지금은 홈과 마법사만 있다. 대시보드와 학습 실행 기록 화면으로 이동할 수 있는 최소 내비게이션을 만든다. 7개 화면 전체(튜터, 자료 보관함, 설정)는 Phase 6~7이므로 Phase 5 에서는 홈(대시보드), 학습 실행 기록, 학습 경로 만들기(기존 마법사)만 연결한다.
- 목표가 없으면 대시보드의 빈 상태에서 학습 경로 만들기로 안내한다.

### 5.8 대시보드 (mockup page-dashboard 기준)
- 컴포넌트를 분리한다: 상단 지표 카드 4개(목업의 네 지표를 따른다), 오늘의 추천 과제 체크리스트(완료 토글), 요일별 스트릭(hit 점), 인사이트 카드.
- 체크 토글은 낙관적 업데이트를 하되 실패하면 되돌리고 오류 표시와 재시도를 제공한다. 저장 중에는 중복 클릭을 막는다.
- 추천 과제는 필수 일정이 아니라는 안내 문구를 둔다. 미완료 과제는 주간 계획에 그대로 남는다.
- 각 위젯의 로딩·빈 상태·오류·재시도 상태를 갖는다.

### 5.1~5.6 학습 실행 기록 화면 (mockup page-execution 기준)
- 레이아웃: 위에 지표 4개(이번 주 학습 시간과 주 목표, 학습 기록 수, 진행 중인 과제 수, 주간 목표 달성률), 왼쪽에 과제별 학습 기록 목록(기간 선택: 이번 주 | 전체), 오른쪽에 기록 폼.
- 새 기록 모드: 과제 선택이 필수다. 과제를 선택하면 타이머 패널이 보인다. 기존 기록을 선택하면 폼이 수정 모드로 바뀌고 "학습 기록 수정 중"으로 분명히 표시되며 타이머 패널은 숨긴다. 저장(변경사항 저장)·취소·삭제가 동작한다.
- 취소하면 편집 전 값으로 롤백한다. 저장 중에는 중복 입력(버튼·필드)을 막는다.
- 팝업을 쓰지 않는다. 삭제 확인도 window.confirm 이 아니라 같은 화면 안의 인라인 확인(예: "정말 삭제할까요? 삭제 / 취소")으로 처리한다.
- 타이머 패널: 서버가 가진 활성 타이머 상태를 따라 표시한다. 새로고침 후에도 진행 중인 타이머가 복원되어야 한다. 시작/종료 버튼 상태가 상태 머신과 맞아야 한다. 이미 다른 과제 타이머가 진행 중이면 409 안내("진행 중인 학습을 먼저 종료·저장하세요")를 보여 준다.
- 타이머 없이 지난 기록을 남길 수 있게 날짜와 시간(분)을 직접 입력할 수 있다. 날짜 입력은 미래 날짜를 막는다(max = 서비스 시간대 오늘).
- 실행 내용, 한 줄 회고, 선택 태그를 입력해 한 번에 저장한다. 회고는 비워도 되고(회고 없는 기록), 기존 회고를 비우면 회고 삭제로 처리한다.
- 쓰기 요청은 client_request_id 를 보낸다. 오류 후 재시도 시 같은 키를 쓴다.
- 사용자 화면 용어: WBS 는 "학습 과제" 또는 "학습 계획", 세션은 "학습 기록"으로 표기한다.
- 화면의 AI 인사이트 영역은 Phase 6.9 에서 연결한다. 이번에는 자리와 부족 안내만 둔다.

### 공통
- 모든 화면에 입력/요청 중/성공/오류/빈 상태를 갖춘다. 요청 타임아웃(기존 apiRequest)을 그대로 쓴다.
- 날짜·주간 계산은 frontend/lib/week.ts 를 쓰고, 필요한 함수는 거기에 추가하며 테스트한다.
- 새로고침 후에도 완료 상태와 진행현황이 일관되게 보인다.

## 테스트 요구사항

- 실제 AI 호출이 필요 없다. Phase 5 는 AI 를 쓰지 않는다.
- Backend(pytest): 기록 생성·조회·수정·삭제 정상 경로, 한 과제에 기록 2건 이상, 회고 생성·수정·삭제, 기록 삭제 시 회고 삭제와 과제 유지, 과제 삭제 시 하위 삭제, 타 UID 의 과제에 기록 생성 거부(403)·타 UID 기록 수정·삭제 거부, 미인증 401·동의 전 403, 미래 날짜·0분·공백 활동·started_at ≥ ended_at 거부, 멱등 재시도, 주간 경계(월요일 00:00 직전·직후, 일요일) 집계, 타이머 시작·종료·409(이미 활성)·새로고침 복원·삭제된 과제의 타이머 정리, 대시보드 요약(빈 상태 기본값, 오늘 추천 우선순위, 지난 요일 미완료가 연체로 나오지 않음, 진행률 계산, 기록 CRUD 후 수치 갱신), 시간대 처리(Asia/Seoul 기준 날짜가 UTC 와 다른 시각 모킹).
- Frontend: typecheck, build, npm test(week.ts 등 순수 함수). 컴포넌트 단위 테스트가 가능한 범위에서 수정 모드 전환, 취소 롤백, 토글 실패 롤백을 테스트한다.
- 실제 uvicorn 을 띄워 HTTP 로 핵심 흐름(동의 → 마법사로 만든 목표·과제 → 기록 2건 저장 → 수정 → 삭제 → 대시보드 요약)을 한 번 확인하고 결과를 보고한다.
- 브라우저로 화면을 직접 조작해 확인하지 못했다면 보고서에 "UI 미검증"이라고 적는다. 사용자가 직접 눌러 볼 시나리오 목록(단계별)을 보고서에 포함한다.

## 열린 결정 (구현 전에 정하고 근거와 함께 문서화해서 보고)

1. 활성 타이머 저장 위치와 계약, 일시정지 포함 여부.
2. minutes 와 started_at/ended_at 이 어긋날 때의 규칙(사용자 보정 허용 방식).
3. 기록 저장이 과제를 자동 완료시키는지(권장: 아니오, 토글만).
4. 회고 단독 삭제 방식.
5. 과제별 누적 시간을 어디서 제공하는지(GET /api/tasks 확장 vs 별도 엔드포인트).
6. 인사이트 충분/부족 기준 값.
7. 동일 과제·같은 날 기록 중복 허용 여부(허용 권장, 이유 기록).

## 함께 처리하면 좋은 항목 (Phase 3·4 검증에서 남은 것)

- require_consented_uid 가 요청마다 users 문서를 읽는 비용(검증 C-1)을 줄일 수 있으면 줄인다. 어렵다면 이유와 함께 보류를 보고한다.
- 목표의 weekly_hours 를 낮추는 PATCH 가 이미 저장된 과제의 시간 예산과 어긋날 수 있다. 대응 여부를 결정해 보고한다.
- docs/phase1_design.md 의 API 와 ERD 를 Phase 5 계약(타이머 상태, 집계 응답)에 맞게 갱신한다.

## 완료 기준 (TASK.md Phase 5)

- 과제 1:N 기록 관계와 기록 수정·삭제 결과가 목록·집계·회고 맥락에 일관되게 반영된다.
- 완료 상태와 진행현황이 새로고침 후에도 일관되게 보인다.
- 오늘 추천 과제를 놓쳐도 과제가 연체·실패 처리되거나 자동 이동하지 않는다.
- 타 UID 의 과제·기록·회고에 접근할 수 없다.
