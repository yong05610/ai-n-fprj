## 필수 수정

### P5-1. 타이머 종료의 멱등 재시도가 409 로 실패한다 (높음)
- 재현: POST /api/timer/start 후 POST /api/timer/finish(client_request_id=f1)가 201 로 성공한다. 응답을 못 받은 클라이언트가 같은 요청을 다시 보내면 200 과 기존 기록이 아니라 409 TIMER_NOT_RUNNING 이 온다. 기록은 1건만 남아 중복 생성은 없지만, 사용자는 저장이 실패한 것으로 보고 같은 내용을 다시 입력하게 된다.
- 원인: backend/main.py 의 finish_timer 가 활성 타이머 확인(없으면 409)을 멱등 키 조회보다 먼저 한다. 첫 성공 시 활성 타이머가 이미 지워져 있다. 현재 멱등 분기는 "기록은 만들어졌지만 타이머 해제 직전에 실패한" 드문 경우에만 닿는다.
- 수정: 같은 user_id 와 client_request_id 로 저장된 study_log 가 있는지를 활성 타이머 확인보다 먼저 조회한다. 있으면 활성 타이머 상태와 관계없이 200 과 기존 기록(회고 포함)을 반환한다(그 안에서 남은 활성 타이머가 같은 요청의 것이면 정리한다).
- 테스트: 시작 → 종료(201) → 같은 키로 종료 재시도(200, 같은 기록 id, 기록 수 1건) 테스트를 추가한다. 키가 다르면 활성 타이머가 없는 경우 409 인 기존 동작은 유지한다.

### P5-2. 목표를 삭제하면 활성 타이머가 남는다 (높음)
- 재현: 과제 t2 에 타이머를 시작한 상태에서 DELETE /api/goals/{id} 가 200 을 반환한다. 이후 GET /api/timer/active 가 이미 삭제된 과제의 활성 타이머(active=true)를 그대로 반환한다.
- 영향: 새 타이머 시작은 TIMER_ALREADY_RUNNING(409)으로 막히고, 화면에는 타이머를 취소하는 버튼이 없다(P5-5). 종료하면 삭제된 과제를 가리키는 고아 기록이 만들어진다. 사용자가 빠져나올 방법이 없다.
- 수정: delete_goal 이 하위 과제를 지울 때 활성 타이머의 task_id 가 그 과제들에 포함되면 users.active_timer 를 비운다. 사용자 데이터 삭제 요청의 정리도 계속 동작해야 한다. 추가로 finish_timer 가 종료 시점에 과제 존재를 확인해, 이미 삭제된 과제의 타이머이면 기록을 만들지 않고 타이머를 정리한 뒤 명확한 오류(예: 409 TIMER_TASK_GONE)를 반환하게 한다.
- 테스트: 목표 삭제 후 활성 타이머 없음, 삭제된 과제의 타이머 종료 거부.

### P5-3. 과제 완료를 토글해도 대시보드 지표가 갱신되지 않는다 (중)
- 위치: frontend/components/Dashboard.tsx 의 toggleTask. 성공 후 summary 를 다시 불러오지 않아 상단의 완료 과제 수와 진행률이 새로고침 전까지 그대로다.
- 요구: TASK 5.9 "완료 상태, 누적 시간, 진행률 집계를 일관되게 갱신" 위반이다. 토글 성공 후 요약을 다시 조회해 지표를 갱신한다(재조회 중 체크 표시가 깜빡이거나 사라지지 않게 처리). 실패 시 롤백과 재시도는 유지한다.

### P5-4. 완료한 과제가 체크리스트에서 사라지고 완료 상태를 볼 수 없다 (중)
- 위치: backend/main.py 의 get_dashboard_summary 가 미완료 과제만 today_tasks 에 담고 is_completed 를 항상 False 로 둔다. 프론트는 토글 직후만 낙관적으로 체크를 유지하고 새로고침하면 완료한 과제가 목록에서 사라진다.
- 영향: PRD FR-06 / TASK 5.8 의 "오늘의 추천 과제 체크리스트와 완료 상태", 완료 기준의 "완료 상태가 새로고침 후에도 일관되게 보인다"와 맞지 않는다. 사용자가 실수로 체크한 과제를 대시보드에서 되돌릴 수도 없다.
- 수정: 추천 우선순위 규칙(오늘 요일 일치 미완료 우선, 없으면 이번 주 다음 미완료)은 유지한다. 단 이번 주 계획의 완료한 과제도 목록에 포함하고 is_completed 를 실제 값으로 채운다. 완료한 과제는 목록 뒤쪽이나 구분된 영역에 두고 체크를 해제할 수 있다. 표시 개수 상한(현재 5)을 정하고 그 규칙을 문서화한다. 이번 주 과제가 전부 완료되었으면 "이번 주 과제를 모두 완료했어요" 같은 안내를 보여 준다.
- 테스트: 완료 과제가 응답에 is_completed=true 로 나오는지, 체크 해제 후 다시 미완료로 나오는지, 지난 요일 미완료가 연체로 표시되지 않는지.

## 일시정지 구현 (사용자 결정: 필수, P5-8)
사용자가 일시정지를 구현하라고 결정했다. 학습 중에 식사, 전화 등으로 멈추는 일이 흔하므로 사용자가 스스로 시간을 관리할 수 있어야 한다. 5-1 의 "일시정지 제외" 결정은 철회한다. TASK.md 5.2 의 상태 머신(idle → running → paused/stopped → saved)을 그대로 구현한다. 뽀모도로는 계속 제외다.

### 설계 지침
- 활성 타이머(users.active_timer)에 누적 시간을 둔다: started_at(최초 시작), accumulated_seconds(일시정지 전까지 쌓인 실제 학습 초), paused_at(일시정지 중이면 시각, 아니면 null), running_since(현재 구간 시작 시각, 일시정지 중이면 null)처럼 필요한 필드를 개발팀이 정하고 문서화한다. 모든 시각은 서버가 정한다.
- 엔드포인트: POST /api/timer/pause, POST /api/timer/resume 을 추가한다. 두 호출 모두 멱등이어야 한다(이미 일시정지 중에 pause 를 다시 보내면 상태를 바꾸지 않고 200, 실행 중에 resume 도 마찬가지). client_request_id 는 기존 방식과 맞춘다.
- GET /api/timer/active 는 상태(running 또는 paused), 서버 기준 누적 학습 초, 현재 구간 시작 시각을 돌려준다. 프론트는 이 값으로 경과 시간을 표시하므로 새로고침해도 복원된다. 일시정지 중에는 시간이 올라가지 않는다.
- 일시정지 중 새 타이머 시작은 TIMER_ALREADY_RUNNING(409)과 같이 거부하고, 응답에 일시정지 중임을 알려 준다.
- 종료(finish): 실행 중이면 현재 구간을 누적에 더하고, 일시정지 중이면 누적 값만 쓴다. minutes 는 누적 학습 시간(분, 최소 1)이다. 사용자가 minutes 를 직접 보낸 값이 있으면 그 값을 우선한다(기존 규칙 유지). started_at 은 최초 시작 시각, ended_at 은 종료 요청 시각이다. 이제 ended_at - started_at 은 일시정지 시간을 포함하므로 minutes 와 같지 않을 수 있다. 기록의 minutes 와 시각쌍 사이에 일치를 강제하는 검증을 넣지 않는다(기존에도 강제하지 않음). 이 규칙을 문서에 명시한다.
- 24시간 규칙: 누적 학습 시간이 24시간(1440분)을 넘으면 자동 계산을 거부하고 수동 입력을 요구한다. 일시정지로 며칠이 지난 타이머도 누적 학습 시간으로 판단하므로 정상 종료할 수 있어야 한다.
- study_date 는 종료 시각이 아니라 최초 시작 시각의 서비스 시간대(Asia/Seoul) 날짜로 둔다(기존 동작 유지).
- 취소(cancel)는 일시정지 중에도 가능하다. P5-1 의 종료 멱등, P5-2 의 목표·과제 삭제 시 정리, 데이터 삭제 시 정리가 일시정지 상태에도 동일하게 동작해야 한다.
- 시작 시의 읽고 쓰기 경쟁(P5-7)은 pause, resume 에도 같은 한계가 있다. 같이 문서화한다.

### 프론트 지침
- 타이머 패널은 상태에 따라 버튼을 보여 준다: 대기(시작), 실행 중(일시정지, 종료, 취소), 일시정지 중(재개, 종료, 취소). 일시정지 중임을 시간 표시 옆에 분명히 표시하고 경과 시간이 멈춘다.
- 새로고침 후에도 상태(실행 중 또는 일시정지 중)와 누적 시간이 복원된다. 서버 값을 기준으로 하고, 화면에서 1초마다 올라가는 시간은 서버가 준 구간 시작 시각으로 계산한다.
- 다른 과제 타이머가 일시정지 상태로 남아 있어도 같은 안내("진행 중인 학습을 먼저 종료·저장하세요")를 보여 준다.
- 요청 중에는 버튼을 막아 중복 클릭을 방지한다. 실패 시 이전 상태로 되돌리고 오류와 재시도를 보여 준다.

### 테스트
- 시작 → 일시정지 → 재개 → 종료에서 minutes 가 일시정지 시간을 제외한 값인지(시각을 모킹해 확인), 일시정지 상태에서 종료, pause 와 resume 의 멱등, 일시정지 중 새로고침 복원(GET active), 일시정지 중 다른 과제 시작 409, 일시정지 중 취소·과제 삭제·목표 삭제 시 정리, 누적 24시간 초과 시 수동 입력 요구, 시각 경계(자정이 지나는 타이머의 study_date 가 최초 시작 날짜).
- 프론트 순수 함수(경과 시간 계산 등)가 있으면 npm test 로 검증한다.

TASK.md 5.2 는 일시정지를 포함해 구현되었음을 반영하고, docs/erd_current.md, docs/phase1_design.md 의 타이머 계약(필드, 엔드포인트)과 docs/phase5_report.md 의 열린 결정 1 을 갱신한다.
