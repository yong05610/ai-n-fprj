# Phase 5D 개발 지시서 — 학습 과제 계획 화면 (page-wbs)

작성: 검증/PM, 2026-10-23. 끝나면 docs/phase5d_report.md 로 보고하고 멈춘다. 5E(관리자), 6B(인사이트), 7 은 시작하지 않는다(뼈대도 만들지 않는다). **선행:** Phase 6 승인(docs/phase6_verification.md).

## 0. 목적과 범위
확정한 계획을 주 단위로 보고, 과제별 추천 요일을 바꾸는 화면을 만든다. 사이드바 "학습 과제 계획"(지금은 "준비 중")을 활성화한다. 과제 완료 토글, 학습 기록은 기존 "학습 실행 기록" 화면이 맡으므로 이 화면에 만들지 않는다. 계획 생성·수정(과제 추가·삭제·시간 변경)도 이 Phase 범위가 아니다.

## 1. 기준
- TASK.md 5D(D.1), mockup/index.html 의 `id="page-wbs"` 섹션, docs/multi_goal_design.md(학습 전환 위젯 F), CLAUDE.md 핵심 결정.
- **화면은 목업 page-wbs 와 나란히 비교해 맞춘다.** 앱 셸·스타일 토큰은 이미 5C 에서 맞춰져 있으므로 기존 클래스를 재사용한다. 목업 전용(.impl-badge, 예시 숫자·이름)은 가져오지 않는다. 보고서에 화면 대조표를 넣는다(규칙: docs/phase5c_dev_prompt.md §1).
- 목업을 읽을 때는 `id="page-wbs"` 섹션 단위로 자른다(한 줄이 길다).

## 2. 화면 구성 (목업 순서)
1. **학습 전환 위젯**(현재 학습 드롭다운): 기존 `GoalSwitch`/`useGoalSwitch` 를 그대로 쓴다. 선택은 users.active_goal_id 에 저장된다(기존 동작).
2. **헤딩:** kicker "WEEKLY LEARNING PLAN", h1 "주간 학습 계획", 설명 "이번 주 목표와 과제를 정하고, 편한 요일에 학습하세요.", 우측 저장 상태 버튼(§3-4).
3. **왼쪽 큰 카드:** 제목 = 과정명(course). 부제 = "현재 {current_level_name} → 목표 {target_level_name} · 주 {weekly_hours}시간"(level 번호 order 는 표시하지 않는다). 우측 pill = "{MM/DD}–{MM/DD} · 이번 주"(보고 있는 주가 이번 주가 아니면 "이번 주" 대신 "지난 주" / "N주 뒤" 등 중립 표현. 연체·지연 표현 금지).
   - 진행 바와 라벨: 왼쪽 "이번 주 예상 {h}시간 {m}분 · 목표 {weekly_hours}시간"(보고 있는 주의 과제 estimated_minutes 합), 오른쪽 "{완료} / {전체} 전체 과업 완료"(이 학습의 **모든 주** 과제 기준. 진행률은 완료 수 / 전체 수이며 시간 가중이나 점수 계산을 하지 않는다).
   - **주 이동:** 카드 머리 아래에 "이전 주 / 다음 주" 버튼(과제가 있는 주 범위 안에서만 이동, 끝에서는 비활성). 처음 열면 **이번 주(Asia/Seoul)** 를 보이고, 이번 주에 과제가 없으면 가장 가까운 과제 있는 주(미래 우선, 없으면 마지막 주)를 보인다. 날짜 계산은 `frontend/lib/week.ts` 만 쓴다(toISOString, 브라우저 로컬 날짜 금지). 이 로직은 순수 함수로 분리해 단위 테스트한다.
   - **과제 행**(order_index 순): 왼쪽 "추천 요일" 레이블과 드롭다운(선택 안 함/월~일, 값은 none, mon~sun), 가운데 제목과 "설명 · 예상 {n}분"(description 이 비면 "예상 {n}분"만), 오른쪽 pill "완료"/"미완료"(status 표시만, 토글하지 않음).
   - 하단 안내 "추천 요일은 참고용입니다. 요일을 바꾸거나 지정하지 않아도 과제는 이번 주 계획에 남습니다."
4. **오른쪽 "AI 학습 조언" 카드:** §4. **"연결된 참고자료" 카드:** §5.
5. 빈 상태: 과제가 하나도 없으면(계획이 비어 있음) 안내 문구와 "학습 경로 설정으로 이동" 링크. 학습이 하나도 없으면 같은 링크의 안내. 로딩·오류·재시도 상태를 둔다(기존 화면 패턴을 따른다).

## 3. 동작 규칙
1. 기존 API 를 재사용한다: `GET /api/goals`, `GET /api/tasks?goal_id=`(전체 주를 한 번에 받아 클라이언트에서 주별로 나눈다), `PATCH /api/tasks/{id}`(suggested_weekday). 과제 목록 조회를 주마다 다시 하지 않는다.
2. 추천 요일은 **마감일이 아니다.** 지난 요일을 골라도, 요일이 지나도 연체·실패·자동 이월·색상 경고를 만들지 않는다. 완료된 과제의 요일도 바꿀 수 있다.
3. 요일을 바꾸면 즉시 저장한다(저장 버튼을 따로 누르지 않는다). 같은 과제를 빠르게 연속해서 바꾸면 마지막 값만 남게 한다(요청 순서가 뒤섞여도 화면과 서버가 같아야 한다).
4. 저장 상태 버튼(목업의 "계획 저장됨 ✓"): 저장 중 "저장 중…", 성공 "계획 저장됨 ✓", 실패 "저장하지 못했어요. 다시 시도"(클릭하면 마지막 변경을 재전송). 실패 시 드롭다운은 서버 값으로 되돌리지 말고 사용자가 고른 값을 유지하되 오류를 보인다(입력 보존).
5. 학습을 전환하면 해당 학습의 계획으로 바뀌고 주 선택은 §2-3 규칙으로 다시 정한다.
6. 서버(PATCH /api/tasks)는 바꾸지 않는다. 요일 값 검증은 기존 `Weekday` 타입이 한다.

## 4. AI 학습 조언 (설계 결정, 계약 변경)
지금은 계획 초안의 `advice` 가 응답에만 있고 확정 때 저장되지 않아 확정 뒤 화면에서 보여 줄 수 없다. 그래서 다음으로 정한다.
- `POST /api/plan/confirm` 요청에 선택 필드 `advice_title`(최대 200자), `advice_content`(최대 4000자)를 추가하고, goals 문서에 그대로 저장한다. 두 필드는 둘 다 있거나 둘 다 없어야 하며(하나만 오면 422), 길이 한도는 AI 초안 스키마(AIPlanDraft)와 같다. 프론트 위저드는 확정할 때 화면에 보이던 조언을 함께 보낸다.
- `GoalResponse` 에 `advice_title`, `advice_content`(둘 다 Optional)를 추가한다. 기존 목표는 값이 없다.
- 이 값은 클라이언트가 보낸 텍스트이므로 서버가 AI 결과로 검증할 수 없다. 본인 UID 의 본인 화면에만 쓰이고 React 가 이스케이프해서 표시하며 로그에 남기지 않는다. 보고서에 이 한계를 적는다.
- 멱등: 같은 client_request_id 재요청은 기존과 같이 저장된 목표를 돌려준다(advice 가 달라도 새로 쓰지 않는다).
- 화면: advice 가 있으면 제목(작은 소제목)과 내용을 "AI 학습 조언" 카드에 보이고 "AI 생성 · 참고용"을 붙인다(6.10). **advice 가 없는 기존 목표**는 AI 조언이 아니라 고정 안내문 "주 {weekly_hours}시간 안에서 가능한 날에 나누어 공부해 보세요. 하루를 놓쳐도 과제는 미완료 상태로 이번 주 계획에 남고, 원하는 날로 옮길 수 있습니다."를 보이고 "AI 생성" 표시는 붙이지 않는다.
- 목업의 "학습 조건 수정 →" 링크는 조건 수정 기능이 없어 가져오지 않는다(PM 이 목업을 고쳤다).
- 계약 문서를 함께 갱신한다: `backend/schemas.py`, `docs/erd_current.md`(goals), `docs/phase1_design.md`(API 표), 프론트 타입. 보고서에 알린다.

## 5. 연결된 참고자료
- 신규 읽기 전용 `GET /api/goals/{goal_id}/references`(require_consented_uid, 소유권은 토큰 UID, 타 UID 403, 없는 id 404). 응답: `{references: [ResourceReferenceItem...], references_notice: str | null}`. 구현은 기존 `match_references(field, course)`/`no_match_notice(field)` 를 재사용한다(plan/generate 와 같은 규칙).
- 화면: 자료명과 "{출처} · {분류}" 를 보이고 url 이 있으면 "원문 보기 ↗". 자료가 없으면 `references_notice` 를 그대로 보여 근거가 있는 것처럼 표시하지 않는다(핵심 결정).
- 목업의 "자료 보관함 보기 →" 링크는 보관함(6.11)이 보류라 가져오지 않는다.

## 6. 메뉴와 연결
- 사이드바 "학습 과제 계획"을 활성화한다. 나머지 비활성 메뉴(참고자료 보관함, 관리자)는 그대로 "준비 중".
- 화면 이동은 기존 해시 규칙(`lib/viewHash.ts`)을 따른다(`#wbs`). 대시보드 등 다른 화면에 이 화면으로 가는 링크를 새로 만들지 않는다(뼈대 금지는 5E 이후 화면에 한한다. 기존 화면의 문구·동작은 바꾸지 않는다).
- 학습 경로 확정 직후 이동하는 화면은 지금 그대로 둔다.

## 7. 하지 않는 것
과제 추가·삭제·시간 변경·순서 변경, 완료 토글, 기록 작성, 목표 수정, 인사이트(6B), 자료 보관함(6.11), 관리자 화면, 배포 설정.

## 8. 테스트
- backend: 확정 시 advice 저장과 조회(GoalResponse), 하나만 오면 422, 길이 초과 422, 멱등 재요청, 기존 목표(advice 없음) 응답, `GET /api/goals/{id}/references`(분야 일치, 불일치 시 notice, 타 UID 403, 없는 id 404, 동의 전 403), 기존 테스트 전부 통과(현재 pytest 319건).
- frontend: 주 선택 순수 함수(이번 주 있음/없음/미래만/과거만/경계, Asia/Seoul 월요일 경계), 요일 값 변환, 마지막 값 우선 처리 로직의 단위 테스트. `npm run typecheck`, `npm test`, `npm run build`.
- 실제 서버 확인(빈 포트, AUTH_MODE=dev STORE_BACKEND=memory 환경변수 덮어쓰기, `.env` 수정 금지, 끝나면 종료): 학습 2개 생성 → 계획 화면에서 요일 변경 → 새로고침 후 유지 → 학습 전환 → 주 이동 → 오류 시 재시도. 브라우저 확인이 어려우면 어떤 항목을 못 했는지 "미검증"으로 적는다.
