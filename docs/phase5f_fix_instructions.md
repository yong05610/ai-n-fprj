# Phase 5F 수정 지시 — 가용 시간 계산과 긴 기간 계획의 분량 (PM, 2026-10-25)

대상: 커밋 ee2c511. 끝나면 docs/phase5f_fix_report.md 로 보고하고 멈춘다. Phase 7 은 시작하지 않는다.

## 1. 판정과 배경
5F 의 핵심(서버 배치, 확정 때 서버 재계산, 목표 전체 예산 검증, 기존 데이터 호환)은 승인한다(docs/phase5f_verification.md). 다음 두 가지는 PM 이 실제 코드와 실제 AI 호출로 확인한 보완 사항이다.

## 2. R1 (필수) 가용 시간을 실제 일수로 계산한다 (개발팀 질문에 대한 PM 결정)
- 문제: 지금 `available_minutes = 주당 분 × week_count` 이고 `week_count` 는 월요일 기준으로 시작일이 속한 주와 목표일이 속한 주를 **통째로** 센다. 시작일이 일요일이면 첫 주는 하루뿐인데 한 주로 센다. PM 실측: 시작일 오늘(일요일), 목표일 60일 뒤 → 실제 61일(8.7주)인데 `week_count` 10, 가용 3000분(= 10주분). 가용이 실제보다 약 15% 크다. 그 결과 "목표일까지 끝나는 계획"이라는 약속이 최대 약 1주 어긋날 수 있다. 개발팀이 보고한 83일 → 13주 사례도 같은 원인이다.
- 결정: **가용 시간 = floor(주당 분 × 포함 일수 / 7)**. 포함 일수 = (목표일 − 시작일) + 1 (양 끝 포함, `clock.py` 날짜만 사용). 단, 결과는 `주당 분 × week_count` 를 넘지 않는다. 시작일이 월요일이고 목표일이 일요일이면 기존과 같아진다.
- **주차 배치와 화면의 주 이동은 지금 방식(월요일 기준 주 구간)을 그대로 둔다.** 바뀌는 것은 **총합 한도(가용 분)** 뿐이다(`available_minutes` 함수와 이를 쓰는 곳: `plan/generate` 의 `max_total_minutes`, `plan/confirm` 검증, 목표 전체 예산 검증(POST/PATCH `/api/tasks`), 대시보드 `plan_available_minutes`, 위저드 요약, 주간 계획 화면).
- 프론트 `frontend/lib/schedule.ts` 의 가용 시간 계산도 같은 규칙으로 바꾸고, **공유 테스트 벡터(`schedule_cases.json`)에 가용 시간 케이스를 추가**해 pytest 와 프론트가 같은 값을 확인한다. 케이스: 월~일 한 주(주당 분 그대로), 일요일 시작·목표 월요일(2일), 수요일 시작·다음 주 금요일 목표, 하루짜리 기간, 83일 기간, 시작일=목표일.
- 위저드 요약 문구는 "주 N주"가 아니라 **"총 {일수}일(약 {주 수}주)"** 로 보인다(소수점 한 자리). 첫 주나 마지막 주가 부분 주이면 "첫 주는 N일만 남아 있어요"를 작은 글씨로 알린다(선택, 가능하면).

## 3. R2 (권고) 긴 기간에서 계획이 지나치게 얇은 문제
- PM 실측(실제 OpenAI): 입문자→실무 개발자, 풀스택 웹 개발, 기간 약 26주, 주 15시간(가용 23400분) → AI 가 과제 **10개, 총 3600분(15%)** 을 만들었다(첫 주 포함 약 4주치). 개발팀 측정(기간 4~12주, 62~92%)과 달리 기간이 길수록 가용 대비 분량이 작아진다. 모델이 과제 수를 기간에 비례해 늘리지 않는다(PM 의 다른 호출들도 6~10개).
- 이 규칙을 **서버가 강제하지는 않는다**(사용자 결정: 시간은 학습자 수준에 따르며 일찍 끝나는 것은 허용). 대신 다음 두 가지를 한다.
  1. **프롬프트와 payload 보강:** payload 에 `week_count`(R1 의 일수 기준 주 수), `suggested_task_count_range`(서버가 계산, 예: 기간 주 수 × 1~2 개로 3~60 안에 clamp), `suggested_total_range_minutes`(가용의 50~100%)를 넣고, 프롬프트에 "총량은 현재·목표 수준의 차이에 맞게 현실적으로 잡되, 가용 시간이 크게 남는데 분량이 너무 적으면 안 된다. 억지로 늘려 채우지 않고, 더 세분화하거나 심화·실습·프로젝트 과제를 구체적으로 포함해 범위를 충분히 덮는다. 같은 과제를 반복하지 않는다"를 추가한다. 이 범위들은 **권고일 뿐 서버 검증으로 거부하지 않는다**(총합 ≤ 가용, 3~60개, 제목 중복 금지만 거부).
  2. **서버가 `coverage_percent`(총합 / 가용, 정수)를 응답에 추가**하고 위저드 요약에 보인다. 값이 40 미만이면 "이 계획은 가용 시간의 {n}% 예요. 더 깊게 배우려면 목표 수준이나 기간을 조정해 보세요." 안내를 요약 아래에 보인다(경고색 없이 중립 톤, 확정은 막지 않는다).
- **개발팀 측정(필수):** 같은 입력으로 **실제 AI 3회**(① 기간 약 26주·주 15시간, ② 약 12주·주 5시간, ③ 약 4주·주 10시간)를 돌려 과제 수, 총합/가용 비율, 모델 호출 횟수, 지연(초)을 숫자로만 보고한다. 목표: ①이 현재(15%)보다 의미 있게 올라가는지 확인(숫자만 보고, 합격 기준은 두지 않는다). 효과가 작으면 PM 이 하한 검증(예: 가용의 40% 미만이면 재시도 사유로 거부)을 도입할지 판단한다.

## 4. 하지 않는 것
주차 배치 방식 변경, 확정 후 재배치, 과제 수 상한 변경(60 유지), 하한 검증 도입(PM 판단 전까지), 화면 레이아웃 변경(위 요약 문구 제외).

## 5. 테스트와 검증 기준
- backend: 가용 시간 공유 벡터와 단위 테스트, `plan/generate`·`plan/confirm`·목표 전체 예산 검증이 새 가용을 쓰는지, `coverage_percent`, 기존 724건이 통과(기대값이 바뀌는 테스트는 목록으로 보고).
- frontend: `schedule.ts` 가용 시간 테스트(공유 벡터), 요약 문구 순수 함수, typecheck/test/build.
- PM 재검증: 시작일 일요일·목표 60일 뒤 입력에서 가용이 3000분이 아니라 2614분(= floor(300 × 61 / 7))이 되는지, 월~일 한 주 기간에서는 기존과 같은지, 실제 AI 로 26주 입력 시 분량 변화를 직접 측정한다.
