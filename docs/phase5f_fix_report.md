# Phase 5F 수정 보고서 — 가용 시간 계산과 긴 기간 계획의 분량

작성: 개발팀, 2026-10-25. 기준: docs/phase5f_fix_instructions.md (대상 커밋 ee2c511). Phase 7 은 시작하지 않았다.

## 요약
- **R1** 가용 시간을 실제 일수로 계산: `floor(주당 분 × 포함 일수 / 7)` (단, 주당 분 × 달력 주 수를 넘지 않음). PM 사례(시작 일요일, 목표 60일 뒤 = 61일, 주 5시간)는 3000분 → **2614분**, 월~일 한 주는 주당 분 그대로.
- **R2** 프롬프트·payload 보강과 서버 `coverage_percent` 응답, 위저드의 사용률 표시와 40% 미만 중립 안내를 넣었다. **실제 AI 측정에서 26주·주 15시간 입력의 분량은 오르지 않았다(13%, PM 실측 15%).** 효과가 작으므로 PM 판단이 필요하다(아래 "R2 측정").
- 테스트: backend pytest **756 통과**(724 → 새 32), frontend `npm test` **132 통과**(115 → 새 17), typecheck 와 build 통과. 실제 Chrome 브라우저 확인 13개 항목 통과.

## 가용 시간 전후 (공유 벡터, 주 5시간 = 300분 기준)
| 입력 | 일수 | 수정 전(달력 주 수 × 300) | 수정 후 |
|---|---|---|---|
| 월~일 한 주 | 7 | 300 | 300 |
| 일요일 시작, 월요일 목표 | 2 | 600 | 85 |
| 수요일 시작, 다음 주 금요일 목표 | 10 | 600 | 428 |
| 하루짜리(수요일) | 1 | 300 | 42 |
| 83일(일요일 시작) | 83 | 3900 | 3557 |
| **PM 사례: 일요일 시작, 60일 뒤** | 61 | **3000** | **2614** |
| 26주(월~일, 주 15시간=900분) | 182 | 23400 | 23400 |
- 월요일 시작·일요일 목표처럼 한 주 단위로 끝나는 기간은 기존과 같다.
- **알아 둘 점:** 하루짜리 기간은 가용이 `주당 분 / 7` 이라 아주 작아진다(주 5시간이면 42분). 한 과제는 최소 10분이므로 3개 과제(30분 이상)가 들어가려면 하루 기간도 가능은 하나 빠듯하다. 이 때문에 기존 테스트 중 하루짜리 기간을 쓰던 것은 과제 시간을 줄여야 했다(아래 목록).

## R2 측정 (실제 OpenAI 3회, 숫자만, 원문 없음)
같은 입력: 분야 "풀스택 웹 개발", 입문자 → 실무 개발자, 시작일 오늘(일요일). 빈 포트 8123, dev + memory, `.env` 미수정, 끝나고 서버 종료 확인. 계획 호출 한도 60초·8000토큰.
| 설정 | 일수 | 가용 | 권고 과제 수 / 권고 총량 | 실제 과제 수 | 총합 | 비율(`coverage_percent`) | 모델 호출 | 지연 |
|---|---|---|---|---|---|---|---|---|
| ① 약 26주, 주 15시간 | 182 | 23400분 | 26~52개 / 11700~23400 | **11개** | 2940분 | **13%** | 1 | 7.1초 |
| ② 약 12주, 주 5시간 | 84 | 3600분 | 12~24개 / 1800~3600 | 12개 | 2070분 | 58% | 1 | 6.4초 |
| ③ 약 4주, 주 10시간 | 28 | 2400분 | 4~8개 / 1200~2400 | 8개 | 2160분 | 90% | 1 | 4.7초 |
- 제목 중복 0, 재시도 0, 타임아웃 0.
- **판단(합격 기준은 두지 않았다):** ①은 11개·13%로 PM 실측(10개·15%)과 거의 같다. 권고 범위(26~52개, 11700분 이상)를 모델이 따르지 않았다. ②는 5h/주 5시간 설정에서 이전 측정(77%)보다 오히려 낮은 58%, ③은 비슷(90%)이다. 즉 **프롬프트 권고만으로는 긴 기간의 분량이 늘지 않는다**(표본이 각 1회라 확정은 아니다).
- 모델은 기간이 길어도 한 번의 응답에서 6~12개 과제만 만드는 경향이 있다. PM 이 고를 수 있는 다음 수단(이번에는 지시대로 구현하지 않음):
  1. 하한 검증: `coverage_percent < 40` 이면 재시도 사유로 거부하고 이전 총합·권고 범위를 피드백으로 전달(재시도 1~2회 비용 증가, 정말 얇은 계획만 거름).
  2. 긴 기간을 구간으로 나눠 두 번 이상 생성(구조 변경이라 PM 협의 필요).
  3. 그대로 두고 화면 안내(`coverage_percent < 40` 중립 안내, 구현함)로 사용자가 기간·목표를 조정하게 함.

## 미검증
- 실제 AI 로 R2 효과가 있는 프롬프트 표현을 찾았는지(위 측정은 지시한 3회뿐이며 효과 없음). 표본이 입력당 1회.
- Firebase 모드, 모바일 폭 화면.
- `coverage_percent` 하한 검증을 넣었을 때의 재시도 비용(PM 판단 전이라 구현하지 않음).

## 열린 결정
1. **R2 하한 검증 도입 여부**(위 1~3). 실측상 권고만으로는 ①이 오르지 않았다.
2. 하루짜리 기간의 가용이 `주당 분 / 7` 로 매우 작아지는 점(주 5시간이면 42분). 의도한 규칙의 결과이나 사용자에게 보일 때 낯설 수 있다.
3. 위저드의 사용률은 편집 즉시 다시 계산한다(서버의 `coverage_percent` 는 생성 시점 값). 확정 후에는 서버 값 기준 화면이 없다.
