## 배치 알고리즘과 공유 테스트 벡터
- 주 수 = 시작일이 속한 주의 월요일부터 목표일이 속한 주의 월요일까지 양 끝 포함. 가용 분 = weekly_hours × 60 × 주 수.
- 과제를 순서대로 타임라인에 붙여 `timeline_start_minutes` = 앞선 과제 분의 누적. 시작 주 = `floor(start / 주당 분)`, 한 과제는 자기 구간과 겹치는 모든 주에 나타나고 주별 예정 분 = 겹치는 길이. 추천 요일 기본값 = `floor((start % 주당 분) × 7 / 주당 분)` → 월~일(정수 계산이라 경계 오차 없음).
- 설계 §3 의 예(주당 300분: 120 / 90 / 150 / 240)는 시작 0·120·210·360, 3번째 과제는 1주차 90분 + 2주차 60분, 요일 월·수·금·화로 두 구현이 같다.
- 벡터 파일: `backend/tests/fixtures/schedule_cases.json`. 케이스: 설계 예, 한 주를 정확히 채움, 한 과제가 3주에 걸침, 주당 분이 작아 한 과제가 매우 긺, 마지막 과제가 마지막 주 끝에 닿음, 과제 1개, 60개, 60개 불규칙, 요일 경계. 주 수 케이스 7개(같은 주, 일요일→월요일, 연말 등).
- **서버가 확정 때 다시 계산하는 값이 진짜다.** 프론트 미리보기는 편집 즉시 보여 주려는 같은 규칙의 복제이며, 확정 후 화면은 서버 값만 쓴다(브라우저 확인에서 미리보기의 과제 수와 서버 저장 타임라인이 이어짐을 확인).

## 일정 고정 한계
확정 후 `PATCH /api/tasks/{id}` 로 `estimated_minutes` 를 바꾸면 합계 검증만 하고 **이후 과제를 다시 배치하지 않는다**(설계 §3). 예: 앞 과제를 늘려도 뒤 과제의 `timeline_start_minutes` 는 그대로라, 서로 겹쳐 보이거나 빈 구간이 생길 수 있다(주별 예정 분은 각 과제의 저장된 시작 위치로 계산). 후속 개선 후보.
- 손으로 만든 과제(`POST /api/tasks`)는 타임라인 끝에 붙는다. 지정한 `plan_week_start` 가 그보다 늦으면 그 주의 시작에 둔다. 이 경로는 6C까지의 화면에서는 쓰지 않는다.

- 과제 수가 60개에 가까운 실제 AI 응답의 지연·형식 오류(이번 실제 호출은 6~10개). 계획 호출 한도(60초, 8000토큰)는 그 대비책이며 실측하지 못했다.

- 서버 제목 중복 비교는 `casefold`, 프론트는 `toLowerCase` 라 독일어 ß 같은 극소수 문자만 다르다(서버가 최종이므로 확정 시 400 으로 안내됨).
