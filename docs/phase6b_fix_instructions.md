# Phase 6B 수정 지시 — 인사이트 숫자 오류와 근거 없는 "반복 어려움" (PM, 2026-10-23)

대상: 커밋 8a22489. 끝나면 docs/phase6b_fix_report.md 로 보고하고 멈춘다. Phase 7 은 시작하지 않는다.

## 1. 무엇이 문제였나 (PM 이 실제 서버에서 실제 AI 호출 1회로 확인)
테스트 데이터: 기록 4건(30, 31, 32, 20분, 합계 **113분**), 회고 **1건**("for 문과 while 문 차이가 아직 헷갈린다").
- **숫자 오류:** AI 가 "총 4시간 53분의 학습"이라고 썼다(실제 1시간 53분). 같은 문장의 "113분"은 맞았다. 모델이 합계를 스스로 계산하다 틀렸다. 서버 검증이 이를 못 잡아 틀린 숫자가 저장되고 **대시보드에도 그대로 표시**된다.
- **근거 없는 반복:** 회고가 1건뿐인데 `difficulty` 에 "반복적으로 언급되었습니다"가 나왔다. 프롬프트의 "두 번 이상 근거가 있을 때만" 규칙을 모델이 어겼고 서버가 강제하지 않는다.
둘 다 PRD FR-06 "근거 없는 내용을 만들지 않는다"에 걸린다. 프롬프트 지시만으로는 막지 못하므로 **서버가 계산과 검증을 맡는다**(CLAUDE.md "AI 결과는 서버가 규칙으로 검증하고 어기면 조용히 고치지 않고 거부·재시도").

## 2. R1 (필수) 숫자는 서버가 계산하고, 글 속 숫자는 서버가 검증한다
1. AI 에 합계를 계산시키지 않는다. `user_payload` 의 `progress`(또는 `window`)에 서버가 계산한 값을 넣는다: `window_record_count`(기간 내 기록 수), `window_total_minutes`(기간 내 합계 분), `window_total_label`(예: "1시간 53분", 60분 미만이면 "45분"), `this_week_minutes`, `this_week_label`, `weekly_target_minutes`, `weekly_target_label`. 표기 규칙을 한 함수로 정해 단위 테스트한다(0분, 59분, 60분, 61분, 120분, 시간만 있는 경우 "2시간").
2. 프롬프트에 "시간·분·건수는 제공된 `*_label`, `*_minutes`, `*_count` 값만 그대로 쓰고 스스로 더하거나 환산하지 않는다"를 명시한다.
3. **서버 검증(`_validate_ai_insight`):** 응답의 `summary`, `difficulty`, `next_action` 에 나오는 모든 시간 표현("N시간", "N분", "N시간 M분", "N건", "N회")을 추출해, 서버가 보낸 값(각 label 과 minutes, count 와 개별 기록의 minutes, 개별 기록 수)에 속하는지 확인한다. 속하지 않는 숫자 표현이 있으면 `AIRetryFeedback`(재시도, 위반한 표현을 validation_error 로 알려 준다)으로 거부한다. 소진되면 기존대로 저장 없이 502. 허용 집합과 추출 규칙(정규식)을 보고서에 문서화한다. 날짜·요일 숫자("10월 23일", "3일 동안"처럼 시간이 아닌 숫자)는 검증 대상이 아니다.
4. 위 오류 사례를 그대로 회귀 테스트로 만든다: 가짜 AI 가 "총 4시간 53분"을 돌려주면(실제 113분) 거부·재시도되고, "1시간 53분"이나 "113분"이면 통과한다.

## 3. R2 (필수) "반복되는 어려움"은 근거가 있을 때만
- 입력 회고가 2건 미만이면 `difficulty` 는 반드시 빈 문자열이어야 한다. 비어 있지 않으면 거부·재시도한다(validation_error: "회고가 2건 미만이면 difficulty 를 비워야 합니다").
- 회고가 2건 이상이어도 모델이 근거 없이 쓸 수 있지만 의미까지 서버가 검증할 수는 없다. 대신 프롬프트에 "difficulty 를 쓰려면 서로 다른 회고 두 건 이상에서 같은 어려움이 확인되어야 하고, 그렇지 않으면 빈 문자열"이라고 이미 있는 규칙을 유지하고 입력 회고 건수(`reflection_count`)를 payload 에 넣어 모델이 알 수 있게 한다.
- 화면: `difficulty` 가 비어 있으면 줄 자체를 숨기는 기존 동작을 유지한다.
- 회귀 테스트: 회고 1건 + 가짜 AI 가 difficulty 를 채움 → 거부·재시도, 비움 → 통과. 회고 2건 이상이면 채워도 통과.

## 4. R3 (권고) 금지 표현 검사의 과잉 여부 보고
`INSIGHT_FORBIDDEN_TERMS` 에 "실패", "마감", "지연" 이 포함되어 "실패해도 괜찮아요", "마감일이 없어요" 같은 무해한 문장도 거부된다(개발팀이 보고서에 이미 적음). 이번에는 **바꾸지 않는다.** 다만 실제 AI 호출 3회 동안 거부·재시도가 몇 번 일어났는지, 502 로 끝난 적이 있는지를 보고서에 적어 사용자 테스트 전에 PM 이 판단하게 한다.

## 5. 하지 않는 것
화면 변경, 새 API, 쿨다운·멱등·저장 구조 변경, 프롬프트의 어조 변경. 기존 pytest 460건과 프론트 66건이 통과해야 한다.

## 6. 검증 기준 (PM)
- backend pytest 전부 통과(실제 건수, 신규 테스트 포함), frontend typecheck/test/build.
- 실제 서버(빈 포트, dev + memory 환경변수 덮어쓰기, `.env` 수정 금지)에서 PM 이 §1 과 같은 데이터(기록 4건 113분, 회고 1건)로 **실제 AI 를 2회** 호출해, 합계 표기가 서버 값과 일치하고 `difficulty` 가 비어 있거나 근거 있는 경우에만 채워지는지 확인한다. 개발팀도 같은 시나리오를 한 번 확인해 보고서에 결과(상태와 숫자 일치 여부만, 원문 없이)를 적는다.
