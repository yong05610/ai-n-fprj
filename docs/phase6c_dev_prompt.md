# Phase 6C 개발 지시서 — 학습 자료 접근성 개선 (검토된 링크 확장 + 검색 링크 + 튜터 키워드)

작성: 검증/PM, 2026-10-24. 끝나면 docs/phase6c_report.md 로 보고하고 멈춘다. Phase 7 은 시작하지 않는다(뼈대도 만들지 않는다). **선행:** Phase 6B 수정(docs/phase6b_fix_instructions.md)이 검증된 뒤 시작한다(같은 파일 main.py, prompts.py 를 고치므로 충돌을 피한다).

## 0. 왜 하는가 (개선 이력 IMP-004, docs/ai_improvement_log.md)
사용자가 AI 튜터와 계획 화면을 보고 "자료를 제시할 때 실시간 웹검색이 없어 답변이 한정적이고 빈약해 보이며, 학습에 참고할 실자료도 부족하다"고 지적했다. 원인은 (1) 검토된 자료가 10건뿐이라 대부분의 분야에서 "참고한 등록 자료가 없어요"가 나오고, (2) 자료가 없으면 학습자가 다음에 무엇을 찾아봐야 하는지 아무 단서도 없다는 점이다. 실시간 웹검색은 출처 신뢰성 검증, 비용·지연, 프롬프트 주입 위험 때문에 MVP 에서 도입하지 않는다(결정 2026-10-24). 대신 **서버가 만든 링크만** 쓰는 세 가지로 개선한다. **AI 가 URL 을 쓰게 하지 않는다.**

## 1. 만드는 것
### A. 검토된 링크 자료 추가 (데이터)
- `docs/phase6c_resource_links.md` 의 표(31건, PM 이 URL 을 실제로 열어 확인)를 `backend/data/rag_documents.json` 에 **링크 전용 자료**로 추가한다(`chunks` 는 빈 배열, `verified: true`, `verified_at: "2026-10-24"`, `license: "링크만 제공(원문 복제 없음)"`, 새 필드 `tags: [..]`(문서의 tags 열), `link_only: true`). 기존 10건은 그대로 둔다. `rag_chunks.json` 은 건드리지 않는다.
- 링크 전용 자료는 **튜터 답변의 출처(sources)로 쓰지 않는다**(근거는 조각만). 검색(`rag.search`)의 대상도 아니다.
- 표의 URL 과 제목을 임의로 바꾸지 않는다. 확인 열이 "200만 확인"인 항목은 그대로 넣되 보고서에 적는다.

### B. 분야 매칭 개선 (`resources_catalog.match_references`)
지금은 분야 문자열의 **첫 토큰**이 정확히 같을 때만 매칭해("Python 개발"→python), AI 가 만든 자유 입력 분야("웹 프론트엔드 개발자", "VIBE CODING", "영어 회화" 등)에는 거의 맞지 않는다. 다음으로 바꾼다.
1. 입력 = 학습의 `field` + `course`(필요하면 목표 문구 제외). 토큰화는 기존 `_TOKEN_PATTERN`(영문·숫자, 한글) 소문자.
2. 각 자료의 점수 = (입력 토큰과 자료 `tags` 토큰이 **정확히 같은** 개수) + (입력 토큰이 자료 `category` 의 분야·과정 토큰과 정확히 같은 개수). 부분 문자열 일치는 쓰지 않는다(Java 가 JavaScript 에 맞는 오류 방지, 기존 회귀 테스트 유지). 한글은 기존 규칙처럼 길이 2 이상 조사 접두(rag.py `_tokens_match` 와 같은 한글 접두 규칙)만 허용할지 개발팀이 정하고 보고서에 적는다.
3. 점수 상위 최대 5건. 점수 0 이면 매칭 없음. 일반어("개발", "기초", "입문", "코딩", "학습", "공부", "과정")는 점수에 넣지 않는다(불용어 목록으로 관리).
4. **정밀도 우선:** 맞지 않는 자료를 보여 주느니 안 보여 주는 편을 택한다. 기존 `match_references` 테스트(분야 일치 필수, Java≠JavaScript, "UX 디자인"≠"SQL 기초")는 모두 통과해야 하고, 바뀌는 기대값은 보고서에 목록으로 적는다.
5. 호출 경로는 그대로: `plan/generate` 응답의 `references`, `GET /api/goals/{id}/references`. 분야가 하나도 안 맞으면 기존 `references_notice` 와 아래 C 의 검색 링크가 나온다.

### C. 직접 검색해 보기 링크 (서버 생성)
- 새 순수 함수(예: `search_links(field, course, extra_terms)`): 검색어 = `{course} {field}` 같은 학습 정보와 선택적 추가어. **AI 출력이나 클라이언트가 보낸 URL 은 쓰지 않는다.** 서버가 고정 템플릿으로 만든다: 구글 검색(`https://www.google.com/search?q=` + 퍼센트 인코딩), 유튜브 검색(`https://www.youtube.com/results?search_query=` + 인코딩). 필요하면 "공식 문서" 검색어 변형을 하나 더(예: `{검색어} 공식 문서`). 최대 3개. 검색어는 200자로 자른다.
- 라벨은 반드시 "직접 검색해 보기 (검토 전 외부 링크)"처럼 **검토된 자료가 아님**을 드러낸다. `target="_blank" rel="noreferrer"`.
- 노출 위치: (1) 주간 계획 화면 "연결된 참고자료" 카드 하단(자료가 있어도 없어도), (2) 튜터 우측 "참고자료" 패널과 답변 말풍선 하단, **출처가 없는 답변에서** "더 찾아볼 키워드"와 함께.
- `GET /api/goals/{id}/references` 응답에 `search_links: [{label, url}]` 추가(필드는 항상 존재). `plan/generate` 응답은 변경하지 않는다.

### D. 튜터: 함께 보면 좋은 링크와 더 찾아볼 키워드
- `AITutorAnswer` 에 `search_keywords: List[str]`(0~3개, 각 1~30자) 추가. **출처가 없는 답변(`used_source_ids` 가 비었거나 검색 결과가 없음)** 일 때 모델이 학습자가 이어서 찾아볼 키워드를 낸다. 서버 검증: 개수·길이, `http`, `://`, `www.` 포함 시 거부(URL 금지), 위반은 조용히 고치지 않고 재시도(기존 validator). 관련 질문이 아니면(`relevant=false`) 키워드는 버린다.
- 서버는 키워드가 있으면 답변 아래에 줄 "더 찾아볼 키워드: a, b, c"를 붙이고(기존 "참고한 등록 자료가 없어요" 안내 앞), 그 키워드로 C 의 검색 링크를 만든다. 메시지 저장 필드에 `search_keywords`(저장) 를 추가한다. 링크 URL 은 저장하지 않고 응답 때 만든다.
- 답변에 출처가 **있을 때**도, 현재 학습(`active_goal_id`)과 매칭되는 링크 자료(A)를 최대 2건 `related_links: [{title, source_name, url}]` 로 보여 준다("함께 보면 좋은 자료"). 출처(근거)와 시각적으로 구분한다. `related_links` 는 서버가 `match_references` 로 만들며 AI 가 정하지 않는다.
- 튜터 프롬프트(`TUTOR_SYSTEM_PROMPT`)에 규칙 추가: 자료가 없을 때도 일반 지식으로 충분히 구체적으로 답하되(예시, 단계, 흔한 실수), 이어서 찾아볼 키워드 2~3개를 `search_keywords` 로 제안한다. 자료를 근거로 든다고 말하지 않는다는 기존 규칙은 유지한다.

## 2. 화면
- 주간 계획 화면 "연결된 참고자료" 카드: 검토된 자료 항목(제목, "{출처} · {분류}", 원문 보기) 아래에 구분선과 소제목 "직접 검색해 보기", 검색 링크 2~3개 + 작은 글씨 "검토 전 외부 링크예요." 자료 없음 안내(`references_notice`)가 있어도 검색 링크는 보인다.
- 튜터: 출처 없는 답변 아래 "더 찾아볼 키워드: …" 줄, 우측 "참고자료" 패널에 "함께 보면 좋은 자료"(related_links)와 "직접 검색해 보기" 링크. 기존 "AI 생성 · 참고용", "참고한 자료가 없어요" 문구와 3열 레이아웃은 유지한다.
- 목업 page-wbs, page-tutor 와 나란히 비교하고 보고서에 대조표를 넣는다. 목업에 없는 요소(검색 링크 소제목, 키워드 줄)는 "구현에만 있음(의도적)"으로 적는다(PM 이 목업을 맞춘다).

## 3. 하지 않는 것
실시간 웹검색 호출, AI 가 URL 을 쓰는 기능, 링크 본문 크롤링·복제, 자료 보관함 화면(6.11), 사용자 자료 업로드, 조각(`rag_chunks.json`) 추가.

## 4. 보안·품질 기준
- 모든 URL 은 서버 템플릿 또는 `rag_documents.json` 값이다(응답에 AI 가 쓴 URL 이 들어갈 경로가 없다는 것을 테스트로 보인다: 가짜 AI 가 `search_keywords` 에 URL 을 넣으면 거부).
- 검색어 인코딩: 한글·공백·`&`, `#`, `"` 가 들어간 학습 이름이 쿼리 문자열을 깨뜨리거나 파라미터를 주입하지 못한다(테스트).
- 로그에 질문·답변·키워드 원문을 남기지 않는다.
- 기존 pytest(6B 수정 후 건수)와 프론트 테스트가 통과해야 한다.

## 5. 테스트
- backend: `rag_documents.json` 로딩(링크 전용 자료 31건 + 기존 10건, link_only 는 `rag.search` 대상 아님), `match_references` 매칭(자유 분야 문자열 예: "웹 프론트엔드 개발자"→웹 개발 자료, "영어 회화"→영어, "데이터 분석 입문"→pandas 등, Java≠JavaScript, 일반어만 있는 입력은 매칭 없음, 최대 5건), `search_links`(인코딩, 최대 3개, 200자 제한), `GET /api/goals/{id}/references` 에 `search_links`, 튜터 `search_keywords` 검증(URL 거부, 개수·길이, relevant=false 면 버림), 출처 없을 때 키워드 줄 부착, 출처 있을 때 `related_links` 2건 이하, 저장 필드, 기존 튜터 테스트 호환.
- frontend: 검색 링크·키워드 표시 순수 함수 테스트, typecheck, test, build.
- 실제 OpenAI 호출은 **필요한 만큼만 최대 2회**(자료 있는 질문 1회, 자료 없는 분야 질문 1회, 빈 포트, dev + memory 환경변수 덮어쓰기, `.env` 수정 금지, 끝나면 종료). 브라우저로 두 화면의 새 요소를 확인하고 못 한 것은 "미검증"으로 적는다.
