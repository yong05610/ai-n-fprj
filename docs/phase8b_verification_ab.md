## 개발팀의 결정 요청에 대한 답
| 질문 | 답 |
|---|---|
| 중복 검사를 DNS·요청 앞으로 옮김(설계는 8번째) | **승인.** 외부 접근이 줄어 더 안전. 설계서 §3-3 을 이에 맞게 고쳤다 |
| 128KB 초과 페이지는 거부하지 않고 앞 128KB 만 읽음 | **승인.** 설계의 "앞 128KB 까지만 읽고 중단"과 같다. 제목·설명은 앞쪽에 있다 |
| MDN, Next.js 의 출처 이름이 카탈로그에 두 가지 | 먼저 나온 이름 사용 **승인.** 카탈로그 이름 통일은 별도 정리 사항(급하지 않음) |

## 개발팀 후속 요청
1. **기존 실패 8건 수정(테스트만).** `tests/test_phase5_exec.py` 의 고정 날짜를 `backend/clock.py` 의 오늘·이번 주 기준 상대 날짜로 바꾼다. 제품 코드는 바꾸지 않는다. **별도 커밋**으로 하고 8B 와 섞지 않는다. 다른 테스트 파일에도 같은 고정 날짜가 있는지 찾아 목록을 보고한다(주가 바뀔 때마다 깨질 수 있다).
2. (권장, 단계 C 와 함께) **DNS 조회 시간도 전체 8초에 포함**한다. 지금은 DNS 대기(최대 3초)가 리다이렉트 홉마다 별도로 더해져 최악의 경우 8초를 3초 이상 넘는다(코드상 추정, 시험으로 재현하지는 않음). 한 요청의 총 상한을 지키면 관리자 화면의 대기 시간이 예측 가능하다.
3. (권장) DNS 조회 스레드 풀(4개)은 응답 없는 조회가 쌓이면 이후 조회가 대기한다. 관리자 한 명이 쓰는 기능이라 위험은 낮지만 조회 시간 초과 시 풀이 막히지 않는지 한 줄 시험을 추가한다.
