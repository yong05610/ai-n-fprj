# MVP 이후 개선 후보 (사용자 테스트 후 판단)

Phase 8(사용자 테스트) 관찰과 설문에서 필요성이 확인된 항목을 Phase 9(피드백 반영)의 우선순위 후보로 올린다. 각 항목은 결정 일자와 근거를 남긴다.

## 1. 타이머 일시정지 / 재개
- 결정: 2026-10-20 사용자 결정으로 MVP 구현에서 제외했다. 사용자 테스트에서 필요성을 확인한다.
- 배경: TASK.md 5.2 의 상태 머신에는 paused 가 있었지만, PRD FR-03 은 학습 시작·종료와 시각 기록만 요구한다. 식사나 전화처럼 학습 중간에 멈추는 사용 패턴에서 불편할 수 있다.
- 현재 대응: 종료하고 기록을 여러 건으로 나눠 저장하거나(과제 하나에 기록 여러 건 가능) 시간을 직접 보정한다.
- 테스트에서 확인할 것: 테스터가 중간에 멈추고 싶어 했는가, 기록을 나눠 저장하는 방식을 불편해했는가, 시간 보정을 얼마나 자주 썼는가.
- 구현 시 설계 메모(검증팀 제안): users.active_timer 에 누적 학습 초와 일시정지 시각을 추가하고 POST /api/timer/pause, /resume 을 둔다. 종료 시 minutes 는 일시정지를 뺀 누적 학습 시간이며 시작·종료 시각 간격과 달라질 수 있다. 저장된 study_logs 의 구조를 바꿀 필요가 없다. 서버 시각 기준, 멱등, 새로고침 복원을 유지한다.
- 규모: 작음(엔드포인트 2개, 필드 추가, 프론트 버튼 상태 2개, 테스트).

## 2. 종합 분석의 지난 주 보기
- 결정: 2026-10-22 Phase 5B 에서 만들지 않기로 했다(PM 답변, docs/phase5b_fix_instructions.md P5B-2-4).
- 내용: GET /api/analytics/overview 는 이번 주(월~일)만 반환한다. 주 이동 쿼리(예: week_start 파라미터)와 화면의 이전/다음 주 버튼은 후속 후보다.
- 테스트에서 확인할 것: 테스터가 지난 주 투입 시간을 다시 보고 싶어 했는가.

## 3. POST /api/goals 의 client_request_id 멱등
- 결정: 2026-10-22 수용(PM 답변, P5B-2-6). MVP 화면은 POST /api/plan/confirm 만 쓰므로 POST /api/goals 에는 client_request_id 가 없다.
- 내용: 이 경로를 화면에서 쓰게 되면 plan/confirm 과 같은 멱등 키(재시도 시 200)를 추가해야 한다. 멱등 조회는 겹침 검사보다 앞에 둔다.

## 4. 실행 화면의 "과제 완료 처리" 링크 (목업 page-execution)
- 결정: 2026-10-22 Phase 5C 검증에서 만들지 않기로 했다(PM 답변). 대시보드의 오늘의 추천 과제에서 완료 토글이 가능하다.
- 내용: 목업의 실행 화면 과제 그룹에는 완료 처리 링크가 있다. 기능 추가이므로 후속 후보다.
- 테스트에서 확인할 것: 테스터가 실행 화면에서 바로 완료 처리를 못 해 불편해했는가.

## 5. POST /api/goals 의 시작일 고정 (참고)
- `POST /api/goals` 는 시작일을 "이번 주 월요일"로 고정한다(5B 수정 2 검증 기록). 화면이 쓰지 않는 경로라 영향은 없다. 화면에서 쓰게 되면 start_date 를 받도록 바꾼다.

## 6. 참고자료 없음 안내문 분리 (Phase 5D 검증 2026-10-23)
- `no_match_notice` 끝의 "아래 계획은 등록 자료 없이 AI가 생성한 일반 계획입니다."는 계획 생성 화면용 문장이라 주간 계획 화면(page-wbs)에서는 어색하다.
- 후보: 서버 문구를 화면용과 계획 생성용으로 나누거나 화면에서 마지막 문단을 빼는 대신 필드를 분리한다.
