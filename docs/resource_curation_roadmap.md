# 학습 자료 큐레이션 고도화 로드맵 (MVP 이후 단계적 업그레이드 근거)

작성: 검증/PM, 2026-10-25. 관련: docs/ai_improvement_log.md IMP-004, TASK.md Phase 12.3·12.4, 서비스기획서 §10("검증된 학습 자료 확대 및 자료 업로드"), docs/post_mvp_backlog.md.

## 1. 왜 필요한가 (근거)
| 구분 | 근거 | 출처 |
|---|---|---|
| 사용자 지적 | "AI 답변이 한정적이고 빈약해 보이고, 학습에 참고할 실자료가 부족하다"(2026-10-24) | 사용자 의견, IMP-004 |
| 현재 규모(측정, 2026-10-25) | 검토된 자료 41건(본문 조각이 있는 문서 10건·조각 53개, 링크 전용 31건), 분야 분류 9개(AI·머신러닝, JavaScript, Python 개발, 데이터 분석, 백엔드 개발, 영어, 웹 개발, 컴퓨터 공학, 협업 도구) | `backend/data/rag_documents.json`, `rag_chunks.json` |
| 구조적 한계 | 자료 쓰기 경로가 없다(서버는 읽기만, 파일은 저장소에 고정). AI 는 자료를 찾지도 저장하지도 않는다. 분야가 늘어도 자료는 저절로 늘지 않는다. | 코드(`rag.py`, `resources_catalog.py`) |
| 품질 위험 | 본문 조각은 사람 검토 없이는 쓰지 않는다(IMP-001). 자유 입력 분야 때문에 매칭이 취약했다(IMP-004: 실제 테스트 학습이 빈 결과였던 것을 수정). | IMP-001, IMP-004 |
| 운영 부담 | 링크가 시간이 지나면 깨지며 지금은 수동 확인(docs/pre_deploy_checklist.md)뿐이다. | 6C 검증 |
| 측정 한계 | 어느 분야에서 자료가 비었는지 집계가 없다(로그에 사용자 입력을 남기지 않는 원칙 때문). | CLAUDE.md 핵심 결정 |

결론: 서비스 질의 상당 부분이 자료의 폭과 신뢰성에 달려 있고, 현재는 사람이 손으로 늘리는 구조뿐이다. 따라서 **"후보를 모으는 일은 자동·반자동으로, 서비스에 노출하는 일은 사람 승인 후에만"**이라는 원칙으로 단계적으로 고도화한다.

## 2. 원칙 (모든 단계에 적용)
1. **노출 전 승인:** AI 가 찾은 자료, 사용자가 제안한 자료는 승인 전에는 서비스에 보이지 않는다(IMP-001 의 `verified` 흐름을 확장). 틀린 링크, 저작권, 스팸, 프롬프트 주입 위험을 승인 단계에서 막는다.
2. **근거와 참고를 분리:** 튜터의 근거(출처)는 팀이 검토한 본문 조각만, 링크는 "참고자료"(IMP-004). 이 구분을 단계가 올라가도 유지한다.
3. **AI 가 URL 을 쓰지 않는다:** 모든 URL 은 서버 템플릿 또는 승인된 데이터 값이다.
4. **개인정보:** 사용자 입력 원문, 회고, AI 응답 원문을 집계나 후보 큐에 저장하지 않는다. 분야 수준의 건수와 해시/정규화된 분류만 쓴다.
5. **업로드 파일은 받지 않는다:** 사용자 제안은 링크만 받고 관리자 검토를 거친다(개인정보·저작권·악성 파일 위험).
6. **변경은 측정으로 정당화:** 단계마다 시작 기준선과 목표 지표를 정하고 개선 이력(docs/ai_improvement_log.md)에 전후를 기록한다.

## 3. 단계별 로드맵
| 단계 | 내용 | 선행 조건 | 규모 | 성공 지표(기준선은 Phase 8 에서 측정) |
|---|---|---|---|---|
| **S0 (완료, MVP)** | PM 큐레이션 + URL 실제 열림 확인, 링크 31건, 분야 매칭 개선, 서버 생성 검색 링크 | 6C 완료 | 완료 | 자료가 1건 이상 연결되는 학습 비율(측정 예정) |
| **S1 분야 확장(수동, 요청 시)** | 테스트에서 자료가 비었던 분야부터 PM 이 조사·검증해 링크를 추가(요청하면 즉시 가능). 배포 때 링크 재확인 | Phase 8 데이터 | 소(분야당 반나절) | 자료 없음 분야 수 감소 |
| **S2 자료 공백 집계** | 튜터 답변에서 출처가 없었던 경우와 계획 화면에서 자료가 비었던 경우를 **분야·과정 분류와 건수만** 집계(원문·UID 없음). 관리자가 상위 공백 분야를 본다 | 5E 관리자 화면, 개인정보 설계 검토 | 중 | 상위 공백 분야 목록, 공백률 |
| **S3 후보 수집 큐** | AI 와 PM 이 후보 링크를 "검토 대기" 컬렉션에 쌓는다(서비스에는 비노출). 후보마다 근거 분야, 출처 도메인, 확인 상태를 기록 | S2 | 중 | 승인율, 후보당 검토 시간 |
| **S4 관리자 "참고자료 관리"** | 5E 에서 "준비 중"으로 남긴 메뉴를 구현: 후보 승인·반려, 분야 태그 수정, 자료 수·링크 상태 조회. 승인된 것만 서비스에 반영(배포 없이 반영되도록 읽기 경로를 DB 로 이전) | S3, Firestore 쓰기 경로 설계 | 대 | 승인부터 노출까지 시간, 분야별 자료 수 |
| **S5 자료 평가 신호** | 참고자료·출처에 "도움이 됐어요/아니에요"(개인 식별 없이)를 받아 품질 신호로 쓴다. 낮은 평가 자료는 관리자 검토 목록에 올린다 | S4 | 중 | 도움 비율, 낮은 평가 자료 처리 시간 |
| **S6 링크 자동 점검** | 주기적으로 모든 링크를 점검해 깨진 것을 관리자에게 알린다(자동 숨김은 하지 않고 승인자가 결정) | S4 | 소 | 깨진 링크 탐지까지 시간 |
| **S7 사용자 링크 제안(선택)** | 사용자가 링크만 제안하면 S3 큐로 들어가 같은 승인 절차를 거친다. 제출 제한·중복 제거 포함 | S4, 정책 결정 | 중 | 제안 대비 승인율, 스팸 비율 |
| **S8 AI 후보 발굴 고도화(선택)** | 허용 도메인 목록 안에서만 웹검색 도구로 후보를 찾아 S3 큐에 넣는다(노출은 승인 후). 실시간 응답 경로에는 쓰지 않는다 | S4 | 대 | 승인 가능한 후보 비율, 비용 |

단계 간 순서는 S1 → S2 → S3 → S4 가 기본 경로이고 S5, S6 은 S4 뒤에 병행할 수 있다. S7, S8 은 S4 이후 효과와 운영 부담을 보고 결정한다. TASK 의 Phase 12.3(자료 확대·업로드), 12.4(관리자 검수)가 이 로드맵의 S1, S4, S7 에 해당한다.

## 4. 진행 판단 기준 (Phase 8·9 결과로 결정)
- **S1 즉시:** 테스터가 학습하려는 분야에서 "자료 없음"이 확인되면 그 분야를 바로 추가한다(저비용).
- **S2~S4 착수:** 사용자 테스트 설문의 "참고자료가 도움이 되었는가(1~5)" 중앙값이 3 이하이거나, "자료가 부족하다"는 의견이 테스터의 40% 이상일 때(수치는 5명 기준으로 2명 이상이면 후보 판단, 사용자 결정으로 조정 가능).
- **S5 착수:** S4 이후 자료가 늘었는데도 평가가 낮은 경우.
- **S7, S8 착수:** 분야 확장의 운영 부담이 PM 수동 처리를 넘을 때.
- 위 기준을 만족하지 않으면 현재 구조(S0~S1)를 유지하고 다른 우선순위(Phase 9 개선, 안정화)를 먼저 한다.

## 5. 위험과 대응
| 위험 | 대응 |
|---|---|
| 승인되지 않은 링크 노출 | 모든 단계에서 노출 전 승인, 승인 필드는 서버가 읽어 거르기(IMP-001 방식) |
| 저작권, 라이선스 | 링크만 제공하고 본문 복제 금지(6C 규칙), 본문 조각은 개발팀 요약을 PM 이 검토 |
| 프롬프트 주입(외부 글) | 외부 본문을 AI 입력에 넣지 않는다(링크 메타데이터만), S8 도 후보 단계에서만 사용 |
| 개인정보 | 집계에 원문·UID 없음, 분야 단위, 최소 건수 미만이면 표시하지 않기 검토 |
| 운영 과부하 | 승인 큐 크기 제한, 우선순위(공백 상위 분야부터) |
| 비용 | 후보 발굴은 비실시간 배치로, 일일 한도 |
| 링크 깨짐 | S6 자동 점검, 배포 전 수동 점검 병행 |

## 6. 변경 이력 기록 규칙
단계를 구현하면 docs/ai_improvement_log.md 에 IMP 항목(발생 현상, 원인, 결정, 설계, 효과)으로 기록하고 이 문서의 단계 상태를 갱신한다. 효과는 기준선 대비 측정값만 쓴다.
